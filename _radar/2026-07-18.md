## 候选

### 1. Claude Code subagent 的 harness 硬约束（hidden contract 集）
- **是什么**：一组 Claude Code subagent 的框架契约，官方 API doc 少提、blog 实测得出——
  (a) subagent 定义**省略 `tools` 字段 = 继承主对话全部工具**（含 MCP），不是零工具 →
  read-only 研究 agent 必须显式 `tools: Read, Grep, Glob`；
  (b) **subagent 不能再 spawn subagent**（无嵌套委派），`Agent` / `AskUserQuestion` /
  `ScheduleWakeup` / `EnterPlanMode` 等对 subagent 不可用；
  (c) **background subagent 自动拒绝任何会弹权限的工具调用**、且无法问澄清问题 → 后台写操作
  可能**静默失败却返回"成功形状"的输出**；
  (d) context 隔离**不对称**：只有 final message 回 parent；subagent 只看到 delegation prompt +
  自身 system prompt + CLAUDE.md/memory/git-snapshot，**看不到** parent 对话历史/已读文件；
  (e) subagent 定义 **session 启动时加载**，改定义文件要重启 session（除非走 `/agents` 界面）。
- **为什么可能跟你相关**：直接补 `techniques/coordination-patterns.md` + `techniques/worker-instructions.md`
  （它们讲概念工作流，缺 Claude-Code-specific 的 harness 契约）；"background 写静默返回成功形状
  输出"正好咬 `guidelines/code/validation.md` / `techniques/adversarial-verification.md`
  （"tests passing ≠ correct"的 subagent 版）；形态上是 `guidelines/claude-code/hook-conventions.md`
  的姊妹篇。可能新开 `guidelines/claude-code/subagent-contracts.md`。
- **促成门槛**：单一 blog 源，需对**官方 Claude Code subagent 文档逐条核实**（可用 claude-code-guide
  agent）；工具可用性清单 / nesting depth 可能版本相关，易过时。核实后确认与 repo 已知的
  subagent 并行/background 行为不重复。
- **来源**：https://hidekazu-konishi.com/entry/claude_code_subagents_and_orchestration_guide.html （2026-06-07, blog）

### 2. LLM review 对"否定式约束"的系统性盲区 → 用确定性 gate 兜
- **是什么**：LLM 统计上 underweight negation → spec 里写成 **"DO NOT ..."** 的约束是概率式
  review **最容易 false-negative** 的地方（Critic 恰恰在否定约束上漏检最多）。推论：否定式约束
  不能只靠 LLM review 兜，**必须配确定性 gate checkpoint**。（同源另有已覆盖点：Critic 走 fresh
  session 防 drift、Critic 只当 gatekeeper——这些 `coordination-patterns.md` 的 fresh-worker /
  `requesting-code-review` 已有，不重复推。）
- **为什么可能跟你相关**：正交补强 `techniques/fact-forcing-gate.md`（advisory vs hard control——
  否定约束正是"advisory review 兜不住、需要 hard gate"的具体高发点）+ `techniques/adversarial-verification.md`
  （MFIC 的 oracle/mechanical check：否定约束应上 `enumerate-then-adjudicate` 式机械检查）+
  `guidelines/workflow/code-review.md`。给"什么时候不能只靠 agent review"一个具体可操作判据。
- **促成门槛**：blog 源，但"LLM 弱于否定"有真实学术基础（促成前确认有可引的一手研究）；想清楚落到
  哪条——`fact-forcing-gate.md` 加一节，还是 `code-review.md`，还是 `adversarial-verification.md`。
- **来源**：https://asdlc.io/patterns/adversarial-code-review/ （2026-06-30, blog）

### 3. Anthropic 官方"给 agent 写工具"的量化设计原则（用于扩 UnrealMCP fork）
- **是什么**：三篇 Anthropic 一手工程博客给的**可量化**工具设计规则——
  (a) **少而合并的高层工具** > 1:1 包 API 端点（一个工具内部做多步，如 `schedule_event` 替
  `list_users`+`list_events`+`create_event`）；
  (b) **tool-use examples**——工具定义里塞 1-5 个具体样例调用，复杂参数准确率 **72%→90%**；
  (c) **工具定义按需/渐进加载**（code-execution-with-MCP 把工具当文件系统 API：150K→2K token；
  Tool Search 的 `defer_loading: true`：~85% 降且不破 prompt cache）；
  (d) **evaluation-first + agent-in-the-loop 迭代工具**：跑 eval → 把 transcript 喂回 Claude Code
  自动找糙点 refactor → held-out set 复测防过拟合。
- **为什么可能跟你相关**：你**在扩 UnrealMCP fork**（`skills/ue/unrealmcp-usage` 的 "Extending
  UnrealMCP"）——加自定义 command 时这套直接可操作（合并工具 / 给 example / 别一股脑塞定义）。
  "按需加载"跟 `techniques/context-budget-audit.md` 的三档加载模型**同构**（那条管 guideline/skill
  加载，这条管工具定义加载）。可能补 `unrealmcp-usage` skill 或新起一条"扩 MCP 时的工具设计"。
- **促成门槛**：一手源可靠；但要判断你扩 fork 的**频率/规模**值不值得成文（two-strike：是否已在多处
  感受到工具设计 friction）；纯 API feature 部分（Programmatic Tool Calling / `defer_loading` 参数）
  对 Claude Code 用户是 **awareness 非可配置规则**，别照搬成"规则"。
- **来源**：https://www.anthropic.com/engineering/writing-tools-for-agents ,
  https://www.anthropic.com/engineering/advanced-tool-use ,
  https://www.anthropic.com/engineering/code-execution-with-mcp （2025-09~11, primary）

### 4. CLAUDE.md 行数甜区 + skill 库 sprawl 数值护栏
- **是什么**：把 context 卫生**数值化**的规则——CLAUDE.md 甜区：~200 行内每轮全读、过 ~500 行
  开始 skim 信号密度崩（**另一源说 ~40 行 / ~400 行明显质量下降，数字互相矛盾**）；skill 库 sprawl：
  团队攒 40-50 个但 top 5 占 ~90% 调用、长尾为零 → **硬上限 ~20 + 季度退休 review** 删低于调用
  阈值的。
- **为什么可能跟你相关**：给 `techniques/context-budget-audit.md` 补**具体数值锚**（现在它是定性的：
  只讲 always-loaded 累积成本 + skill description 长度）；你的 AGENTS.md 本身巨大、skill 已 ~20+，
  "skill 上限 + 退休 cadence"表面直接适用。
- **促成门槛**：**本轮最低置信度**——blog-only、两源数字互相矛盾（200/500 vs 40/400）；团队维度
  （named owner / PR 强制 / 人均调用指标）明确属 `knowledge-promotion.md` 排除的"组织政策"要剥掉；
  促成前先**实测你自己的 CLAUDE.md/AGENTS.md 在多长时 harness 开始 skim**（可探针验证），别照搬
  博客数字。跟 seen.md 已大量覆盖的 context-engineering 临近。
- **来源**：https://www.digitalapplied.com/blog/claude-code-anti-patterns-team-adoption-failure-modes-2026 ,
  https://ai.rundatarun.io/ai-development-agents/claude-code-best-practices （2026, blog）
