## 候选

### 1. Stop Hook 的 8 次连续阻断上限 ⭐⭐⭐ 【已核源：引语逐字属实】

- **是什么**：官方 best-practices 文档明文——Stop hook 做确定性验证 gate 时，连续阻断 8 次后 Claude Code **强制 override 并结束回合**。原文（coordinator 逐字核对过）：
  > "a Stop hook runs your check as a script and blocks the turn from ending until it passes. **Claude Code overrides the hook and ends the turn after 8 consecutive blocks.**"
- **为什么相关**：直接补 `guidelines/claude-code/hook-conventions.md`（当前无此条）。更重要的是冲击 `techniques/fact-forcing-gate.md` 的 advisory/hard 框架——Stop hook 原被视为"最接近 hard 的一层"，8-block override 意味着它**结构上也是 advisory**。长自主运行的验证门控设计必须考虑这个上限。
- **促成门槛**：无——一手官方文档 + 引语已逐字核对。**本轮最推荐先促成**。
- **来源**：https://code.claude.com/docs/en/best-practices（"Give Claude a way to verify its work" 节）

### 2. 动态 Workflow 命名模式（Tournament / Generate-and-Filter / Classify-and-Act）⭐⭐⭐ 【已核源，含修正】

- **是什么**：claude.com 官方 blog 命名了 **6 种** workflow 模式：Classify-and-act / Fan-out-and-synthesize / Adversarial verification / Generate-and-filter / Tournament / Loop until done。其中 Tournament（N agent 各自尝试 + judge 做 pairwise 比较，"comparative judgment is more reliable than absolute scoring"——引语逐字核对属实）、Generate-and-filter、Classify-and-act 三种不在 `techniques/coordination-patterns.md`。
- **⚠️ 对 worker 原报告的两处修正**（coordinator 核源发现）：worker 称"7 种"，实际 blog 命名 **6 种**；worker 把 "Quarantine" 列为并列命名模式，实际它**不是**——只是 Triaging at Scale 一节里的一句做法描述（"barring the agents that read untrusted public content from taking high-privilege actions"）。该做法本身仍有价值（对 `fact-forcing-gate.md` 的 advisory/hard 框架是新机制），但引用时别称其为官方命名模式。
- **为什么相关**：补 `techniques/coordination-patterns.md`（当前只有 fan-out / serial-chain / iterative-retrieval）。Tournament 的 pairwise>absolute 论断与 `adversarial-verification.md` 的 de-anchored judge 互补。
- **促成门槛**：已核源。促成时用修正后的事实（6 种、Quarantine 单列为做法而非模式）。
- **来源**：https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code

### 3. Agent Teams 架构 ⭐⭐ 【存在性已交叉确认】

- **是什么**：Claude Code v2.1.178+ 实验性功能（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）。与 subagent 的本质区别：队友是完全独立的 Claude Code 会话，可**直接互相通信**（SendMessage）、共享任务列表（pending/in-progress/completed + 依赖链）、自领任务（文件锁防竞态）、plan approval gate。best-practices 页独立提及（"automated coordination of multiple sessions with shared tasks, messaging, and a team lead"），存在性可信；细节字段未逐条核。
- **为什么相关**：跟 `skills/collaboration/multi-session-coordination`（hook-based 多会话）和 `role-lane-coordination`（人工 mailbox 协调）是**第三种机制**。三者 trade-off 对比（共享任务列表 vs lease hook vs mailbox / 自领 vs 显式分配 / 直接通信 vs 人工路由）值得补进 collaboration 域。
- **促成门槛**：实验性、版本绑定强。促成前跑一次真实体验；架构 pattern（共享任务列表 / 自领 / plan gate）框架无关可先记。
- **来源**：https://code.claude.com/docs/en/agent-teams

## 附：Model Worker 代跑的运维知识（比候选更值钱的部分）

这轮的真正产出是把「worker（kimi-k3 via Claude Code harness）代跑 heavy workflow」这条路径的**边界摸清了**。5 轮任务 + 2 次探针、约 $26、与 ModelWorkerMCP main lane 七封信往返，钉死的事实：

### Worker 运行时边界（按发现顺序）

1. **字符串 `Workflow.args` 曾被 daemon 白名单拒收**（`capability-profiles.ts` 只认对象）——所有内置 workflow 都要字符串 args，等于全灭。已修（`4f4a142`）。
2. **`StructuredOutput` 曾不在工具白名单**——`agent({schema})` 必死。已修（同 commit）。
3. **`StructuredOutput` 大载荷被"取消"（B-009，未解，不在 daemon 层）**：12 字节过、3~6 KB 被取消（`toolDenialKind: "cancelled"`，非策略拒绝；daemon 新加的 deny 可观测性对它零记录=判决性证据）。**含义：worker 跑不了任何 schema-bound 的真实 workflow**（deep-research 的 SCOPE_SCHEMA 输出就是 3-5 KB）。方向在取消/上游截断，疑与「工具调用参数通道」对长参数的处理有关。**绕法：无 schema 的 textmode workflow**（agent 回纯文本 JSON、JS 解析）——`radar-textmode.js`。
4. **同一底层拒绝表现成两种上层错误**：模型选择重试→`retry cap (5) exceeded`；模型服从那句 "STOP and wait" 话术→`completed without calling StructuredOutput`。排查时别当成两个 bug。
5. **后台 workflow 交付物曾在任务终结后才产生、MCP 侧拿不到（B-010）**：worker 提交 workflow 后必然立刻结束回合（5/5 复现，包括它逐字承诺"我不会提前结束回合"之后）——**brief 侧对抗模型的回合收敛行为 0/5，不要再试**。已修（`9827cb3`：流式输入 + `background_tasks_changed` 电平信号，等后台清空才 finalize）。
6. **daemon 重启必换端口，MCP client 必须人工重连**（4 次全中，无自动恢复）。症状 `fetch failed`。重启前先想清楚有没有别的会话在跑任务。
7. **kimi-k3 网关无 prompt caching**（`cache_write` 恒 0）——多轮长 context 任务每轮全量重发，run 1 单线程手搜烧 $14.07 的主因。
8. **usage 上报可疑时以 daemon 的 `runtime_reported` 为准**，transcript 聚合会出现 cache_read>0 但 cache_write=0 的矛盾。

### 协作 pattern 验证

- **coordinator 验收 ≠ 重跑核验**：抽查 URL 可达 + 引语逐字 + stats 自洽 + seen.md 黑名单比对，成本 2 次 WebFetch，抓出 worker 报告里 3 处错误（"7 种模式"、"Quarantine 是命名模式"、"上轮已确认 deep-research 不可用"——最后一条是 worker 把自己的调用失败误诊成结论写进交付物）。
- **worker 自述不可信时去读运行记录**：`%LOCALAPPDATA%\model-worker-mcp\runtime-contexts\...\workflows\wf_*.json` 的 `agentCount` / `totalTokens` 是"扇出真跑没跑"的硬判据（0 = 没跑，别信 worker 说跑了）。
- **跨 repo bug 报告用 mailbox + 行级根因 + 复现包**，对方当天修完三条（B-007/B-008/B-010）。「递证据不递意见」的具体形态：diff 行号 + 三种调用形状对照表 + $0.84 可复跑探针。
- **轮询 loop 的存活条件要跟它等的东西同层**：mailbox 轮询卡在自己这端的 MCP 断连上空转 10 轮——loop 检测不到也修不了自己所处进程的依赖状态，那类阻塞靠人推。
