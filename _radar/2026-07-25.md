#### 1.1 写 / 格式化（Write & Format）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **clang-format** | 基于 `.clang-format` 配置，LLVM/Google/Chromium/Mozilla/WebKit 内置风格 | ✅ 完全 CLI | ✅ 适合 | A（官方文档） |
| **clangd** | LSP server，基于 `compile_commands.json`，可同时跑 clang-tidy checks | ✅ 启动后通过 LSP 通信 | ✅ 适合，但需要 LSP 客户端 | B（LLVM 源码） |
| **include-what-you-use** | 分析头文件依赖，生成 `#include` 修正 | ✅ 完全 CLI | ✅ 适合 | B（LLVM 源码） |

**已知 hidden contract / 陷阱：**

- **clang-format 与 clang-tidy 的 `FormatStyle` 配置可能冲突**：clang-tidy 内部也读 `.clang-format` 做某些检查的格式化上下文，两边配置不一致会导致 clang-tidy 误报格式相关 warning。**修法**：一个项目只维护一个 `.clang-format`，clang-tidy 的 `FormatStyle` 设成 `file`。（来源：LLVM 官方文档 + 社区共识 → 层级 B）
- **clangd 的 `--clang-tidy` 标志**：clangd 可以边补全边跑 clang-tidy check，但**默认启用全部 check**，很容易在大型项目上把 clangd 变慢。**修法**：在 `.clangd` 配置文件里显式指定 `Checks: '*'` 然后 exclude 掉慢的组（如 `-readability-*`）。（来源：LLVM 文档 + 社区踩坑 → 层级 B）
- **`compile_commands.json` 缺失**：clangd 和 clang-tidy 都依赖此文件。CMake 默认不生成，必须 `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`。**修法**：`CMakePresets.json` 设为默认值。（来源：CMake 官方文档 → 层级 A）
- **clang-format 的 `ColumnLimit: 0`**：关闭列宽限制会让 clang-format **跳过大量格式调整**，但也会让某些对齐规则（AlignConsecutive*）表现异常。**修法**：设一个具体值（80/100/120），别设 0。（来源：社区共识 → 层级 C）
- **IWYU 的假阳性**：`include-what-you-use` 对 template 特化、宏展开的依赖分析经常误判，删掉需要的头文件。**修法**：用 `#include <foo.h> // IWYU pragma: keep` 强制保留，或只用在 CI 的 warning 模式不直接 block。（来源：LLVM 文档 + 社区经验 → 层级 B/C）

#### 1.2 审 / 静态分析（Static Analysis）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **clang-tidy** | 90+ 个 check 分 13 组（bugprone / readability / modernize / performance / portability / concurrency / cert / misc / llvm / google / abseil / boost / cppcoreguidelines） | ✅ 完全 CLI | ✅ 适合，但需注意配置 | A（LLVM 文档） |
| **clang-analyzer** | 在 clang-tidy 内部（`clang-analyzer-*` 组），深度 path-sensitive 分析 | ✅ 通过 clang-tidy 跑 | ✅ 同上 | A（LLVM 文档） |
| **cppcheck** | 独立工具，部分检查与 clang-tidy 重叠，但有一些独特的 MISRA / 安全检查 | ✅ 完全 CLI | ✅ 适合 | B（官方文档） |
| **PVS-Studio** | 商业，深度分析，UE 项目有专门支持 | ✅ CLI（但需要 license） | ⚠️ 需要 license 处理 | D（商业产品） |
| **ReSharper C++ CLI** | JetBrains 的 CLI 分析工具（`inspectcode`） | ✅ CLI | ⚠️ Windows + license 依赖 | D（商业产品） |

**已知 hidden contract / 陷阱：**

- **clang-tidy 的 check 分组很重要**：`clang-analyzer-*` 组是**路径敏感的**，耗时长但也更准；`readability-*` 组大多 false positive 少但噪音多；`modernize-*` 组适合一次性迁移，**不适合常驻 CI**（建议作为一次性重构检查，然后关掉大部分）。**修法**：CI 常驻跑 `bugprone-*` + `performance-*` + `concurrency-*` + `clang-analyzer-*`，`modernize-*` 和 `readability-*` 按需手动跑。（来源：LLVM 社区 + 行业实践 → 层级 C）
- **clang-tidy 的性能问题**：`clang-analyzer-*` 组的 alpha 检查（`alpha.*`）默认不启用，且路径分析在复杂函数上可能跑几分钟。**修法**：CI 设置 `--timeout=60`，对超时的 check 跳过而非失败。（来源：LLVM 官方文档 → 层级 A）
- **clang-tidy 的 `NOLINTBEGIN` / `NOLINTEND`**（LLVM 14+）：可以批量抑制一段代码，但需要 clang-tidy 14 以上。之前版本只有 `// NOLINT` 单行抑制。**修法**：确保 CI 的 clang-tidy 版本 >= 14 才用这个功能。（来源：LLVM 文档 → 层级 A）
- **clang-tidy 与 `system_header` 的交互**：默认不检查 `-isystem` 目录的头文件（第三方库），但某些 .clang-tidy 配置可能意外覆盖。**修法**：`HeaderFilterRegex` 明确只匹配项目源码路径。（来源：LLVM 文档 → 层级 A）
- **cppcheck 的 `--inconclusive` 标志**：开启后给出更多结果，但 false positive 率显著上升。**修法**：不开 `--inconclusive`，或者只开在单独的分析 job 里，不 block CI。（来源：cppcheck 官方文档 → 层级 A）

#### 1.3 编译（Build）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **CMake** | 构建系统生成器，支持 Presets（`CMakePresets.json`）统一配置 | ✅ 完全 CLI | ✅ 适合 | A（官方文档） |
| **ccache / sccache** | 编译缓存，sccache 支持 S3/GCS 远程缓存 | ✅ 完全 CLI | ✅ 透明集成 | B（官方文档） |
| **Ninja** | 比 MSVC 的 msbuild 快数倍的构建工具，天然增量 | ✅ 完全 CLI | ✅ 适合 | A（官方文档） |
| **LLVM/Clang** | 编译器前端，支持 `-Wall -Wextra -Wpedantic -Werror` 等 | ✅ 完全 CLI | ✅ 适合 | A（官方文档） |
| **MSVC** | Windows 编译器，`/W4 /WX` 等效 | ✅ 完全 CLI | ✅ 适合 | A（官方文档） |

**已知 hidden contract / 陷阱：**

- **`CMAKE_EXPORT_COMPILE_COMMANDS` 必须在 `project()` 之前设置**，否则 CMake 可能不生成 `compile_commands.json`。**修法**：在 `CMakeLists.txt` 顶部 `cmake_minimum_required()` 之后立即设 `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)`，或在 `CMakePresets.json` 的 `cacheVariables` 里设。（来源：CMake 官方文档 + 社区踩坑 → 层级 A/B）
- **ccache 与 MSVC**：ccache 在 Windows/MSVC 上支持有限，需要用 `ccache --set-config compiler_type=msvc` 或切换到 sccache。**修法**：Windows 上用 sccache 而非 ccache。（来源：ccache 官方文档 → 层级 A）
- **`-Werror` 的可能风险**：升级编译器版本后，新 warning 会让旧代码编译失败。**修法**：不用全局 `-Werror`，而是用 `-Werror=` 只把特定 warning 设为 error（如 `-Werror=return-type`），或只在 CI 的特定 build config 下启用。（来源：社区共识 → 层级 C）
- **CMakePresets.json 比 toolchain 文件更推荐**：`CMakePresets.json` 可以统一管理 build type、cache variables、environment、test preset、vendor 配置等。**修法**：新项目用 CMake 3.21+ 的 `CMakePresets.json`，不再用 `-D` 参数链。（来源：CMake 官方文档 → 层级 A）
- **Windows 上的 260 字符路径限制**：`<项目>/Intermediate/Build/<平台>/<配置>/<模块>/<文件>.obj` 这种深层路径很容易撞。**修法**：启用 Windows 10 的 `EnableLongPaths` 注册表项，或缩短项目路径。（来源：社区共识 → 层级 C；本仓库已有 `guidelines/ue/build-plugin-limitations.md` 记录）

#### 1.4 测试（Test）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **GoogleTest / GoogleMock** | 最广泛使用的 C++ 测试框架，参数化测试、death test、type-parameterized test | ✅ 完全 CLI（`--gtest_filter` / `--gtest_repeat` / `--gtest_shuffle`） | ✅ 适合 | A（官方文档） |
| **Catch2** | header-only 可选，BDD-style 的 `GIVEN / WHEN / THEN`，比 GoogleTest 更快的编译速度 | ✅ 完全 CLI | ✅ 适合 | B（官方文档） |
| **doctest** | 最轻量，编译最快，功能集最小 | ✅ 完全 CLI | ✅ 适合 | B（官方文档） |
| **CTest** | CMake 自带的测试驱动，不直接跑测试而是包装 test runner | ✅ 完全 CLI | ✅ 适合 | A（CMake 文档） |
| **gcov / gcovr** | 行覆盖率 / 分支覆盖率，gcc 内置，无外部依赖 | ✅ 完全 CLI | ✅ 适合 | A（GCC 文档） |
| **llvm-cov** | Clang 的覆盖率工具，比 gcov 性能更好，支持 `-fprofile-instr-generate` | ✅ 完全 CLI | ✅ 适合 | A（LLVM 文档） |
| **OpenCppCoverage** | Windows 上的覆盖率工具，不需要编译器插桩，而是 hook debug symbols | ✅ 完全 CLI | ✅ 适合 | B（官方文档） |
| **dextool** | 唯一活跃的 C++ mutation testing 工具（LLVM 13+，基于 clang 插桩） | ✅ 完全 CLI | ⚠️ 配置复杂，慢 | D（开源项目） |

**已知 hidden contract / 陷阱：**

- **`--gtest_filter` 的 glob 语法**：`*` 匹配任意字符，`?` 匹配单个字符，`-` 排除。**陷阱**：`TestSuite.*` 匹配 `TestSuite` 下的所有测试，但 `TestSuite_*` 匹配的是名字以 `TestSuite_` 开头的测试套件。**修法**：先用 `--gtest_list_tests` 列出所有测试确认 filter 语义。（来源：GoogleTest 官方文档 → 层级 A）
- **GoogleTest 的 death test 在 Windows Debug 模式下极慢**：`EXPECT_DEATH` 在 MSVC Debug 下可能慢 10-100 倍。**修法**：CI 的 Debug 配置跳过 death test，或移到 Release 配置跑。（来源：GoogleTest 文档 + 社区踩坑 → 层级 B）
- **覆盖率工具的选择取决于编译器**：gcov（gcc）和 llvm-cov（clang）的格式不兼容，但 `gcovr` 两者都支持。**修法**：在 CMake 里根据 `CMAKE_CXX_COMPILER_ID` 条件式设置覆盖率 flag。（来源：gcovr 官方文档 → 层级 A）
- **OpenCppCoverage 的盘符 bug**：某些版本在指定输出路径时，如果路径包含盘符会解析错误。本仓库已有 `techniques/cpp-coverage-and-crap-measurement.md` 记录。（来源：本仓库经验 → 层级 E）
- **mutation testing 在 C++ 上非常慢**：因为每个 mutant 都需要重新编译，`dextool` 虽然用了 clang 插桩优化，但大型项目一轮 mutation 仍可能数小时。**修法**：只对关键模块（核心算法、安全敏感代码）跑 mutation，不覆盖全项目。在 CI 上作为 nightly 而非每 commit 跑。（来源：社区经验 + dextool 文档 → 层级 C/D）
- **llvm-cov 的 `-fprofile-instr-generate` + `-fcoverage-mapping`**：两个 flag 必须同时用，否则生成不完整或空的 coverage 数据。**修法**：CMake 里 `target_compile_options` 和 `target_link_options` 都加上这两个 flag。（来源：LLVM 文档 → 层级 A）

#### 1.5 调试（Debugging）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **gdb** | 最成熟的 Linux 调试器，Python 脚本化，非交互 batch 模式 | ✅ `-batch -ex "run" -ex "bt"` 等 | ✅ 适合，但 batch 模式能力有限 | A（GNU 文档） |
| **lldb** | LLVM 调试器，Python 脚本化更深入，原生支持 `SB*` API | ✅ Python 脚本化（`SBTarget` / `SBProcess` / `SBThread` / `SBFrame`） | ✅ 适合，Python API 比 gdb 更可靠 | A（LLVM 文档） |
| **WinDbg** | Windows 调试器，支持 dump 分析，cdb 是 CLI 版本 | ✅ `cdb -z dump.dmp -c "!analyze -v; q"` | ✅ 适合，但脚本化不如 lldb 成熟 | B（微软文档） |
| **ASan (AddressSanitizer)** | 内存错误检测（use-after-free / out-of-bounds / double-free），运行时 ~2x 慢 | ✅ `-fsanitize=address` 编译 + 链接 | ✅ 透明 | A（LLVM 文档） |
| **UBSan (UndefinedBehaviorSanitizer)** | 未定义行为检测（整数溢出 / 越界 / 空指针等），运行时 ~1.2x 慢 | ✅ `-fsanitize=undefined` 编译 + 链接 | ✅ 透明 | A（LLVM 文档） |
| **MSan (MemorySanitizer)** | 未初始化内存读取检测 | ✅ `-fsanitize=memory` | ⚠️ 必须链接所有库（包括系统库）被 MSan 插桩，否则假阳性 | A（LLVM 文档） |
| **TSan (ThreadSanitizer)** | 数据竞争检测，运行时 ~5-15x 慢 | ✅ `-fsanitize=thread` | ✅ 透明 | A（LLVM 文档） |

**已知 hidden contract / 陷阱：**

- **UBSan 的 `trap` 模式 vs `runtime` 模式**：`-fsanitize=undefined` 默认是 runtime 模式（报错后继续执行），`-fsanitize=undefined-trap` 是 trap 模式（遇到 UB 直接 crash）。**但** trap 模式不区分 UB 类型，所有 UB 都走同一个 trap handler，无法知道触发了哪类 UB。**修法**：CI 用 runtime 模式 + `UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1`，既打印诊断信息又中止。（来源：LLVM 文档 → 层级 A）
- **ASan 的 `LeakSanitizer` 默认只在 Linux 启用**，macOS 需要显式 `ASAN_OPTIONS=detect_leaks=1`，Windows 上不支持 LSsan。**修法**：CMake 里根据平台条件式设置 leak detection。（来源：LLVM 文档 → 层级 A）
- **MSan 的"全量插桩"要求**：MSan 要求**所有**链接的库（包括系统库）都被 MSan 插桩，否则读取未 MSan 插桩的库写入的内存会假阳性。这导致 MSan 在实践中最难用。**修法**：只在完全从源码构建的全量 MSan 配置下使用；或者仅用 ASan + UBSan 组合作为替代（覆盖大部分内存错误）。（来源：LLVM 文档 + 社区共识 → 层级 A）
- **ASan + UBSan 可以同时使用**：`-fsanitize=address,undefined`，**但** ASan + TSan 不能同时使用（它们都做内存拦截，冲突）。（来源：LLVM 文档 → 层级 A）
- **lldb 的 Python 脚本化能力**：`lldb.SBProcess` 提供 `ReadMemory()` / `WriteMemory()`，`SBFrame` 提供 `GetValueForVariablePath()`，`SBThread` 提供 `GetFrameAtIndex()`。可以写完整的自动化调试脚本，包括：crash dump 自动分析、backtrace 批量提取、特定变量值搜索、内存模式匹配。**但** lldb Python 脚本在 Windows 上可能因为 Python 版本不匹配（lldb 捆绑自己的 Python）而踩坑。**修法**：使用 `lldb -b -P` 确认捆绑的 Python 路径，用该路径的 pip 安装额外依赖。（来源：LLVM 文档 + 社区经验 → 层级 B）
- **gdb 的 batch 模式限制**：`gdb -batch -ex "run" -ex "bt"` 可以非交互式跑，但**不能处理断点条件复杂化**，也不能处理程序需要 stdin 交互的场景。**修法**：对复杂场景用 `gdb -batch` 跑 Python 脚本（`-ex "source script.py"`）。（来源：GNU 文档 → 层级 A）
- **WinDbg / cdb 的 `!analyze -v`**：是 Windows crash dump 分析的核心命令，自动分析异常类型、可能根因、故障指令等。**可脚本化**：`cdb -z dump.dmp -c "!analyze -v; .ecxr; kp; q" -logo output.txt`。**但** WinDbg 的脚本语法（`$$` 注释、`MASM` vs `C++` 表达式模式）学习曲线陡峭，且和 gdb/lldb 不兼容。**修法**：考虑用 `lldb` 的 Windows 端口（`lldb -c dump.dmp`）来避免学两套语法。（来源：微软文档 + 社区经验 → 层级 B/C）
- **Sanitizer 的运行时选项**：通过环境变量配置（`ASAN_OPTIONS` / `UBSAN_OPTIONS` / `TSAN_OPTIONS` / `MSAN_OPTIONS`），多个选项用 `:` 分隔。常用选项：`halt_on_error=1`（遇到错误就中止）、`print_stacktrace=1`（打印调用栈）、`suppressions=supp.txt`（抑制已知假阳性）、`log_path=/path/to/log`（输出到文件而非 stderr）。（来源：LLVM 文档 → 层级 A）

#### 1.6 性能分析（Profiling）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **perf**（Linux） | 采样分析器，硬件 PMU 计数器，调用栈、cache miss 分析 | ✅ 完全 CLI（`perf record` / `perf report` / `perf script`） | ✅ 适合 | A（Linux 内核文档） |
| **Tracy** | 采样+插桩混合分析器，GUI 强大，remote capture，低开销 | ⚠️ 需要插桩（`FrameMark` / `ZoneScoped`），CLI 支持有限 | ⚠️ 适合 agent 插桩但查看需要 GUI | B（开源文档） |
| **Intel VTune** | 最深入的 CPU/GPU 性能分析，支持 PMU 驱动采样 | ✅ CLI（`vtune -collect hotspots -r result -target-command=./app`） | ✅ 适合 | D（商业产品） |
| **gperftools** | Google 的采样 CPU profiler + heap profiler | ✅ 完全 CLI | ✅ 适合 | B（开源文档） |
| **`__attribute__((no_instrument_function))`** | 控制插桩的编译属性 | ✅ 编译期 | ✅ 透明 | A（GCC/Clang 文档） |
| **FlameGraph** | Brendan Gregg 的脚本，把 `perf script` 输出转成 SVG | ✅ 完全 CLI | ✅ 适合 | C（开源脚本） |

**已知 hidden contract / 陷阱：**

- **perf 需要 `perf_event_paranoid` 调整**：默认 `/proc/sys/kernel/perf_event_paranoid` >= 2 时非 root 用户不能采样。**修法**：`sudo sysctl -w kernel.perf_event_paranoid=1` 或 `-1`（完全开放）。（来源：Linux 内核文档 → 层级 A）
- **perf 的 `--call-graph dwarf`**：如果使用 `-fno-omit-frame-pointer` 编译，可以用 `fp` 模式（更快）；否则必须用 `dwarf` 模式（走 `.eh_frame`，更慢但不需要 frame pointer）。**修法**：CMake 里 `-fno-omit-frame-pointer` 默认开启，这样 perf 的 fp 模式可用。（来源：社区共识 → 层级 C）
- **Tracy 的插桩开销**：`ZoneScoped` 宏在 Release 下默认是空操作（零开销），但 Debug 下会记录。**陷阱**：如果在 Release 下需要 profiling 数据，必须确保 `TRACY_ENABLE` 宏在 Release 配置下也被定义。（来源：Tracy 官方文档 → 层级 B）
- **VTune 在 Windows 上的 driver 依赖**：需要 `IntelSEP` 驱动来访问 PMU 计数器，在 CI 环境上可能无法安装。**修法**：CI 上用 perf（Linux）或 Windows 上的 `ETW`（Event Tracing for Windows）替代。（来源：Intel 文档 + 社区经验 → 层级 D）
- **FlameGraph 生成的 SVG 是可交互的**：鼠标悬停显示详情、点击放大。**AI 读图**：agent 可以 Read 渲染后的 PNG（本仓库 `gui-visual-machine-gating.md` 有记录），但 SVG 需要渲染后才能直观分析，agent 直接读 SVG XML 不实用。**修法**：agent 调 `perf script` 或者 `perf report --stdio` 拿到文本格式的调用栈统计，比读 SVG 更可靠。（来源：本仓库经验 → 层级 E）
- **采样 profiler vs 插桩 profiler 的选择**：采样（如 perf）低开销但统计性质，适合找宏观热点；插桩（如 Tracy 的 `ZoneScoped`）精确但需要手动标记区域。**agent 操作建议**：先用采样 profiler 找出热点函数，再针对热点函数加插桩做精确分析。（来源：社区共识 → 层级 C）

#### 1.7 反编译 / 二进制分析（Binary Analysis）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **Ghidra**（headless） | SRE 框架，支持反编译、脚本化分析（Python/Jython） | ✅ `analyzeHeadless` 脚本模式 | ✅ 适合，但需 Java 环境 | B（NSA 文档） |
| **IDA Pro**（headless） | 商业反汇编/反编译器 | ✅ `idat64 -B -A -Sscript.py` | ✅ 适合，但需要 license | D（商业产品） |
| **Binary Ninja** | 商业反汇编/反编译，Python API 全面 | ✅ CLI + Python API | ✅ 适合 | D（商业产品） |
| **llvm-objdump / objdump** | 反汇编，符号表，section 信息 | ✅ 完全 CLI | ✅ 适合 | A（LLVM 文档） |
| **nm / llvm-nm** | 符号表列出 | ✅ 完全 CLI | ✅ 适合 | A（LLVM 文档） |
| **strings** | 提取二进制中的字符串 | ✅ 完全 CLI | ✅ 适合 | A（GNU 文档） |
| **readelf / llvm-readelf** | ELF 文件结构分析 | ✅ 完全 CLI | ✅ 适合 | A（LLVM 文档） |
| **dumpbin** | Windows PE/COFF 分析（MSVC 自带） | ✅ 完全 CLI（`/DEPENDENTS` / `/EXPORTS` / `/SYMBOLS` / `/DISASM`） | ✅ 适合 | A（微软文档） |

**已知 hidden contract / 陷阱：**

- **Ghidra headless 模式的生产力**：`analyzeHeadless` 可以批处理反编译 + 跑 Python 脚本 + 导出结果。但 Ghidra 的 headless 模式仍需要图形环境初始化（X11/Wayland），纯 headless（无 DISPLAY）需要额外配置。**修法**：`./analyzeHeadless /tmp/ghidra_proj -import target.exe -postscript analyze.py -deleteProject`，在服务器上需要 `xvfb` 或 `Xvfb` 虚拟显示。（来源：Ghidra 文档 + 社区经验 → 层级 B）
- **`objdump -d` vs `llvm-objdump`**：`objdump` 是 GNU binutils 的一部分，`llvm-objdump` 是 LLVM 等效。两者的输出格式不完全一致，但 `llvm-objdump --x86-asm-syntax=intel` 可以输出 Intel 语法（默认是 AT&T）。（来源：LLVM 文档 → 层级 A）
- **`dumpbin /DEPENDENTS` 对 DLL 部署排错极有用**：列出 PE 文件的 DLL 依赖关系，快速确认缺少哪些运行时库。**agent 可用**：`dumpbin /DEPENDENTS myplugin.dll` 输出所有依赖的 DLL 列表。（来源：微软文档 → 层级 A）
- **strip 的去符号化程度**：`strip`（或 `objcopy --strip-all`）删除符号表，但**.pdb 文件（Windows）和 `.debug` 段（ELF）独立于二进制**。**陷阱**：`strip` 不处理 `.pdb`，Windows 上需要单独管理 `.pdb` 文件。**修法**：CI 打包时，符号版本（`.pdb` / `.debug`）存档到独立位置，交付版本 strip 后发布。（来源：社区共识 → 层级 C；本仓库 `guidelines/ue/build-plugin-limitations.md` 已有相关记录）

#### 1.8 打包 / 分发（Package & Distribute）

| 工具 | 能力边界 | CLI 可脚本化 | Agent 适用性 | 来源层级 |
|------|---------|-------------|-------------|---------|
| **CPack** | CMake 内置打包工具，支持 NSIS / ZIP / TGZ / DEB / RPM | ✅ 完全 CLI | ✅ 适合 | A（CMake 文档） |
| **vcpkg** | Windows 首选 C++ 包管理器，manifest 模式 | ✅ 完全 CLI | ✅ 适合 | B（微软文档） |
| **Conan** | 跨平台 C++ 包管理器，支持多配置 | ✅ 完全 CLI | ✅ 适合 | B（官方文档） |

**已知 hidden contract / 陷阱：**

- **CPack 的 `-G` 参数选择打包格式**：`-G NSIS`（Windows installer）、`-G ZIP`（跨平台压缩）、`-G TGZ`（Linux tarball）、`-G DEB`（Debian 包）。**注意**：`CPACK_PACKAGE_EXECUTABLES` 和 `CPACK_CREATE_DESKTOP_LINKS` 等配置只在 NSIS 下有效。（来源：CMake 官方文档 → 层级 A）
- **vcpkg manifest 模式**（`vcpkg.json`）比 classic 模式更推荐：锁定版本号、支持版本覆盖、支持自定义 triplet。**但** `vcpkg.json` 的 `"builtin-baseline"` 需要从 vcpkg 仓库的 git commit 获取，在 CI 上需要额外注意 vcpkg 的版本与 baseline 对齐。（来源：vcpkg 官方文档 → 层级 B）
- **Conan 在 Windows 上的 MSVC 版本匹配**：Conan 的 binary cache 按 compiler 版本 + 运行时（`MDd`/`MT`/`MTd`/`MD`）做 key，Windows 上 MSVC 版本不一致会导致 cache miss 或 ABI 冲突。（来源：Conan 文档 + 社区经验 → 层级 B）

## 本轮判断

**信号强度：中等偏强。** 工具链的 8 个环节全景图覆盖了本仓库现有的 gap，且大部分内容有官方文档（层级 A/B）支撑。

**最值得优先吸收的内容：**

1. **clang-tidy 的 check 分组策略 + 性能陷阱**（第 1.2 节）—— 直接补充 `guidelines/cpp/`，有明确的 agent 操作建议
2. **Sanitizer 的 CMake 集成 + 运行时选项矩阵**（第 1.5 节）—— 直接补充 `guidelines/cpp/`，每个 sanitizer 的陷阱有官方文档支撑
3. **调试器脚本化（lldb Python / gdb batch / WinDbg cdb）**（第 1.5 节）—— 写 `techniques/debugger-scripting.md`，这是现有 corpus 的明显空白
4. **工具链编排 / CMake Presets 分层**（第 2 节）—— 写 `guidelines/cpp/cmake-presets.md` 或扩充 `INDEX.md`

**需要进一步验证再吸收的内容：**

- **mutation testing 在 C++ 上的实际可行性**（第 1.4 节）—— `dextool` 是唯一活跃工具，但需在真实项目上验证一轮 mutation 的耗时和 mutant 质量
- **Ghidra headless 在纯 C++ 项目上的实用性**（第 1.7 节）—— 本仓库主要场景是 C++ 源码开发，不是逆向工程，Ghidra 的使用场景有限
- **profiling 工具的 agent 接口**（第 1.6 节）—— `perf` 和 VTune CLI 可以脚本化，但 agent 读火焰图 / 分析结果的能力边界需要实测

**不推荐的吸收：**
- 粒度太细的工具参数枚举（如每个 clang-tidy check 的详细说明）—— 应该链接到 LLVM 官方文档，不在这里重复
- 商业工具（VTune / PVS-Studio / IDA）的详细配置—— 依赖 license，不适合写进公开仓库
