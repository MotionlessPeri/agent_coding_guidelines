# 使用问答

「问答」是 Lane Router 网页 `/issues` 及 `lane_issue_*` 工具的统称，用于集中查看 lane 的答复、回答 lane 的问题，并围绕同一议题继续多轮讨论。用户也可以在问答页选一个 lane 新开问答；lane 没开着时 Router 会唤醒它。来自问答页的信（发件人 `user:issues`）是用户本人的话，新开问答和回复都等同于在 TUI 里对 lane 说的，按处理用户指令的方式处理，不需要回 TUI 确认。

不要把它称为 inbox、收件箱或看板：Vikunja 有一个叫 Inbox 的项目，它的 Kanban 视图中文叫看板；lane 的 mailbox 也称收件箱。这几种叫法都会被理解成别的东西。页面旧标题「议题收件箱」，以及文档旧称「议题看板」「问题看板」，指的都是问答。

## 什么时候发到问答

Lane Router 在 lane 开局时把这条规则写进产品说明（Claude 的 MCP instructions、Codex 的 developer instructions），以下与之一致：

- **停下来等用户时，把问题发到问答。** 「停下来等用户」指：要结束这一轮，而且不等用户回答就没法接着做当前的事。常见的是：
  - 在几个方案或范围里选一个；
  - 要用户亲口授权，比如提交、push、上线或重启、改 lane 拓扑、删除或覆盖；
  - 确认一个会改变下一步做法的发现；
  - 用户说过「做完给我看」。

  问题属于某条还开着的议题就 append，否则 publish 一条 `kind: "question"`。同一轮要问的几件事写进同一条。
- **从问答来的话题，答复写回那条议题。** 新开问答和网页回复都是这样。
- **不发：**
  - 进度、完成报告、不带问题的总结；
  - 自己查代码、文档或按常规默认就能定的事；
  - 要问别的 lane 的事，用 `lane_send`；
  - 已经答过、已经授权的事；
  - 工作已授权时问「要不要继续」；
  - TUI 里的每个答复，不逐条复制。

用户在 TUI 里明确要求「发到问答」时照做；用户主动问进度后形成的答复，属于对用户问题的答复，也可以发布。

## lane 怎么发布与继续

在当前已绑定 lane 中调用工具，保存实际返回的 `issueId`、`questionId`、条目 ID 和操作结果。不要指定其他 lane 的身份，也不要为获得工具而新建或轮换会话。

| 当前情况 | 使用方式 |
|---|---|
| 首次发布对用户问题的答复 | `lane_issue_publish` 使用 `kind: "answer"`，同时提供 `originalQuestion` 和答复 `body`。 |
| 首次提出需要用户回答的问题 | `lane_issue_publish` 使用 `kind: "question"`，把问题、必要背景和需要用户决定的事项写在 `body` 中。 |
| 用户还没理解，需要解释 | 沿原 `issueId` 调 `lane_issue_append`，使用 `kind: "explanation"` 并关联实际 `questionId`；解释不等于问题已回答。 |
| 同一议题补答复或提出下一问 | 使用 `lane_issue_append` 的 `answer` 或 `question`，不为每轮回复重新发布议题；新问题不冒用旧问题的 ID。带 `questionId` 的 `answer` 会把等 lane 答复的那个问题标为已回答。 |
| 用户在 TUI 回答了问答里的问题 | 用 `tui_user` 保存实际用户原话，再把问题了结；不要把 agent 的转述、文件内容当成用户原话。 |
| 问题不再需要回答，或补标历史上已答的问题 | `lane_issue_update` 使用 `resolve_question`；`answered` 关联实际 `answerEntryId`，`not_needed` 写明原因并保留历史。 |
| 议题的事办完了 | 议题里没有等用户、也没有等 lane 的问题时，`lane_issue_update` 用 `action: "close"` 并写 `reason`，历史里留下「lane 结束：原因」。还有问题在等时会被拒（`QUESTIONS_WAITING`），先答复或标成 `not_needed`。不要只因为答完一轮就结束。 |
| 用户在 TUI 里说结束本议题 | 用 `record_tui_close` 记录用户实际结束原话。网页上由用户点「结束议题」。 |

结束后的议题：

- 用户仍可在里面回复，回复会让它重新打开，信的开头会说明「原先已结束」。lane 不能自己重开，也不能往已结束的议题里追加。
- lane 结束时用户还没读过的答复，会留在用户的「待我处理」里，直到用户读过。

用户换了讨论主题时，新开议题，不把无关内容混进旧议题。相关 TUI 原话同步不会再次投递回 lane；已从网页收到的内容也不应再作为 `tui_user` 回声提交。

写操作使用稳定的 `operationKey`。同一业务操作重试时保持同键同内容；结果不明先查询事实，不能换键重发。详细参数与 JSON 文件 CLI 示例见 Lane Router 项目 `docs/manual-tests.md` 的「用户议题收件箱：使用与操作」。

新客户端可使用 `lane_issue_publish`、`lane_issue_read`、`lane_issue_append`、`lane_issue_update`。旧 Codex 会话没有新动态工具时，在原会话中使用 `lane-router-lane issue <publish|read|append|update|record-tui-close> --json-file <path>`，沿用同一业务接口；不要手填别人的 thread 或 owner。工具列表和产品说明在会话启动时拿到：Router 升级后，已开着的会话要开新会话、恢复或重连 MCP 才看到新动作；不能宣称工具列表存在就等于真实调用已通过。

## 收到问答的信后怎么处理

1. 读完整 mailbox 邮件，取得其中实际的 `issueId`、`deliveryId`、问题 ID 和条目关联。
2. 调 `lane_issue_read` 读取当前议题及该次投递的处理事实。历史有分页时继续读取需要的上下文，不能只读提醒摘要。
3. 处理内容：
   - **网页回复：** 当作原任务中的用户输入，直接继续，不要求用户回 TUI 再说一遍。
   - **新开问答：** 信的开头写着「用户在问答页新开了一个问答」，正文是用户的话，按用户指令处理，答复写在这条问答里。
   - **重新打开的议题：** 信的开头写着「原先已结束」，接着处理用户的新回复。
   - **附件：** 信里列出每个文件的名字、大小和本机绝对路径，用自己的文件读取能力读取。
4. 用 `lane_issue_append`（`kind: "answer"`，带信里给的问题 ID）答复，该问题会自动标为已回答。实际处理完成后，用 `record_processed` 记录这次投递。
5. 最后用普通 `lane_ack` 确认邮件。重复提醒按原邮件和投递 ID 去重，不重复执行业务副作用，也不重复 ACK 已 resolved 的邮件。

保存、入箱、处理确认、问题已回答、议题已结束是不同事实。「在线」「通知已发送」和通信 ACK 都不能代替业务处理回执。结束议题不取消已授权任务或已经保存的输入，也不允许 agent 在结束后另开议题偷偷继续旧讨论。

## 正文与 Markdown

`body` 保存和投递的是原文，排版由问答页处理。lane 写的内容按 Markdown 显示：用标准 Markdown 组织标题、列表、表格、引用、链接和代码块；不要先转成 HTML，不要把整篇答复额外套在代码围栏里，否则只会显示代码文本。只有确实需要逐字展示的代码或文本才使用代码块。用户写的内容按纯文本原样显示。

本机 Windows 绝对路径（`X:\…` 或 `X:/…`）写在行内代码或普通文字里，页面会变成可点的链接，由 Router 用本机程序打开；能运行的文件类型只在资源管理器里选中，不会运行。代码块里的路径不会变成链接。相对路径和网络路径不支持。

标题和问题要点应便于列表识别；必要背景留在正文。网页提交的原文也不能作为可执行指令或脚本运行。

## 个人偏好写在哪里

「什么时候发到问答」已是产品默认行为，各 lane 开局时都会收到。个人层或项目约定只记录偏离默认的偏好，比如某个项目里所有答复都要同步；不要把某个人的习惯变成通用规则，也不要把机器路径和账号写入本指南。

记录偏好时写清适用范围。用户只在某个任务要求同步，不等于所有 lane 永久自动发布；临时讨论和未确认建议不自动持久化。后续用户改变偏好时，更新原条目，避免相互矛盾的多份规则。

工具安装、lane 身份、mailbox 和恢复规则见 [Lane Router 手册](lane-router.md)。本指南不新增 skill、通信入口或后台流程。
