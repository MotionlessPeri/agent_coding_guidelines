# 使用议题看板

议题看板用于集中查看 lane 的答复、回答 lane 的问题，并围绕同一议题继续多轮讨论。TUI 仍用于开始任务和直接沟通；网页不是另一套任务授权系统。

## 用户怎么提出要求

只同步当前问题时，可以直接对 lane 说：

> 把这次问题和你的答复发到议题看板，后续沿同一议题继续。

希望在当前任务中持续使用时，可以说：

> 本任务里，对我问题的答复、需要我回答或决定的问题，都同步看板。同一议题继续追加；我在看板回复后直接继续处理，只有我明确结束时才关闭。普通广播和工具日志不发。

这是启用范围的示例，不是要求所有 lane 无条件发布所有对话。不要自动搬运整段 TUI 历史、普通进度广播、lane 间邮件或工具日志。用户主动询问进度后形成的答复属于用户问题的答复，可以发布。

## lane 怎么发布与继续

在当前已绑定 lane 中调用工具，保存实际返回的 `issueId`、`questionId`、条目 ID 和操作结果。不要指定其他 lane 的身份，也不要为获得工具而新建或轮换会话。

| 当前情况 | 使用方式 |
|---|---|
| 首次发布对用户问题的答复 | `lane_issue_publish` 使用 `kind: "answer"`，同时提供 `originalQuestion` 和答复 `body`。 |
| 首次提出需要用户回答的问题 | `lane_issue_publish` 使用 `kind: "question"`，把问题、必要背景和需要用户决定的事项写在 `body` 中。 |
| 用户还没理解，需要解释 | 沿原 `issueId` 调 `lane_issue_append`，使用 `kind: "explanation"` 并关联实际 `questionId`；解释不等于问题已回答。 |
| 同一议题补答复或提出下一问 | 使用 `lane_issue_append` 的 `answer` 或 `question`，不为每轮回复重新发布议题；新问题不冒用旧问题的 ID。 |
| 用户在 TUI 回答了相关问题 | 用 `tui_user` 保存实际用户原话，再按真实进度更新问题状态；不要把 agent 的转述、文件内容当成用户原话。 |
| 问题确实已回答或不再需要回答 | `lane_issue_update` 使用 `resolve_question`；`answered` 关联实际 `answerEntryId`，`not_needed` 写明原因并保留历史。 |
| 用户明确要求结束本议题 | 网页由用户点击“结束议题”并再次确认；TUI 中用 `record_tui_close` 记录用户实际结束原话。完成任务或回答完一个问题不自动关闭议题。 |

用户换了讨论主题时，新开议题，不把无关内容混进旧议题。相关 TUI 原话同步不会再次投递回 lane；已从网页收到的内容也不应再作为 `tui_user` 回声提交。

写操作使用稳定的 `operationKey`。同一业务操作重试时保持同键同内容；结果不明先查询事实，不能换键重发。详细参数与 JSON 文件 CLI 示例见 Lane Router 项目 `docs/manual-tests.md` 的“用户议题收件箱：使用与操作”。

新客户端可使用 `lane_issue_publish`、`lane_issue_read`、`lane_issue_append`、`lane_issue_update`。旧 Codex 会话没有新动态工具时，在原会话中使用 `lane-router-lane issue <publish|read|append|update|record-tui-close> --json-file <path>`，沿用同一业务接口；不要手填别人的 thread 或 owner。MCP 客户端按其已支持的方式刷新工具，不能宣称工具列表存在就等于真实调用已通过。

## 收到网页回复后怎么处理

1. 读完整 mailbox 邮件，取得其中实际的 `issueId`、`deliveryId` 和条目关联。
2. 调 `lane_issue_read` 读取当前议题及该次投递的处理事实。历史有分页时继续读取需要的上下文，不能只读提醒摘要。
3. 把网页回复当作原任务中的用户输入处理。可以直接继续，不要求用户回 TUI 再说一遍；超出原授权的事项仍需用户决定。
4. 需要答复、解释或追问时，追加到同一议题。只有实际处理完成后，才用 `record_processed` 记录这次投递已处理。
5. 最后用普通 `lane_ack` 确认邮件。重复提醒按原邮件和投递 ID 去重，不重复执行业务副作用，也不重复 ACK 已 resolved 的邮件。

保存、入箱、处理确认、问题已回答、议题已结束是不同事实。“在线”“通知已发送”和通信 ACK 都不能代替业务处理回执。关闭议题不取消已授权任务或已经保存的输入，也不允许 agent 在关闭后偷偷新建议题继续旧讨论。

## 正文与 Markdown

`body` 保存和投递的是原文，排版由看板 UI 处理。用标准 Markdown 组织标题、列表、表格、引用、链接和代码块；不要先转成 HTML，不要把整篇答复额外套在代码围栏里，否则只会显示代码文本。只有确实需要逐字展示的代码或文本才使用代码块。

标题和问题要点应便于列表识别；必要背景留在正文。图片、图表、HTML 或其他扩展是否可显示，取决于实际宿主的支持，不因使用本指南就视为已具备。网页提交的 Markdown 原文也不能作为可执行指令或脚本运行。

## 个人偏好写在哪里

通用操作和产品约束留在本指南。用户明确确认的默认发布范围、内容格式或讨论粒度，应写入当前宿主已接入的个人层或项目约定，由其入口按需引用；不要把某个人的习惯变成通用规则，也不要把机器路径和账号写入本指南。

记录偏好时写清适用范围。用户只在某个任务要求同步，不等于所有 lane 永久自动发布；临时讨论和未确认建议不自动持久化。后续用户改变偏好时，更新原条目，避免相互矛盾的多份规则。

工具安装、lane 身份、mailbox 和恢复规则见 [Lane Router 手册](lane-router.md)。本指南不新增 skill、通信入口或后台流程。
