# 黑箱刻画第三方 API 的参数语义

## 适用场景

手上有一个**闭源或无文档**的库(静态库 / DLL / 第三方 SDK / 别人写的求解器),要搞清楚某个参数**到底是什么语义** —— 不是"我改的东西对不对"(那是 [`adversarial-verification.md`](adversarial-verification.md)),而是"**别人的这个旋钮控制什么**"。

典型形态:注入已知输入 → 观测输出 → 反推语义。

## 核心问题:扫了没反应,不等于参数没用

黑箱刻画里出现频率最高的一个症状:**扫一个参数从 0 到 1,输出逐值不变。**

最省事的解释是"这个参数没接线 / 没用"。但实测下来这个解释**几乎总是错的** —— 无响应至少有五种原因,真因各不相同,排查手法也不同:

| # | 原因 | 指纹 | 怎么排 |
|---|---|---|---|
| 1 | **参数有两层结构,只设了值没开开关** —— 很多 SDK 的参数是 `(mode, value)` 二元组,默认 mode = Off。光写值等于没写 | 开/关两行**逐值完全相同** | 查参数元数据里有没有 mode / enable 字段;有就显式设 |
| 2 | **用错入口** —— 该参数只在某一条 API 路径上被读。文档里常是一句不起眼的 remark | 扫多个值输出**一模一样**(不是"变化小",是位级相同) | 翻头文件找该参数的 `remarks` / 适用范围;换入口重测 |
| 3 | **没有作用对象** —— 参数修饰的那个行为在当前配置下不发生。例:一个"抵抗被改变"的参数,若没有任何东西试图改它,自然无效 | 被修饰的量 100% 跟随上游 / 或该自由度已被别的约束硬钉死 | 先制造"那件事真的在发生",再扫参数 |
| 4 | **场景没激发** —— 该步骤/该参数管的那件事在当前场景里压根不发生 | 该步骤开/关无差别 | 换一个必然触发它的场景;别用"默认场景"下结论 |
| 5 | **metric 选错** —— 参数**确实生效了**,但你量的那个量看不见它 | 换个量法数字立刻出现 | 见 [`adversarial-verification.md` 的「metric 选错」一节](adversarial-verification.md) |

**第 5 种最危险**,因为它让你得出**反向**结论("参数无效"),而前四种只是让你查不出来。

两个实例:一个"抵抗"参数施加在关节 A 上,却去量关节 B 的**位置**位移 → 全程纹丝不动;数**全局**旋转来判断"哪些关节参与了求解" → 六种求解器全报"全部参与",跟文档逐条对不上(改数**局部**旋转后立刻精确吻合 —— 因为全局旋转会被父关节带着动)。

**碰到无响应,先把这五种枚举一遍,再考虑"它没用"。**

## 比较维度不独立时,先把混淆变量拆开

想知道「参数 X 对结果的影响」,常见做法是准备几组不同的输入对象(几个骨架 / 几份配置 / 几个数据集)去比。**陷阱是:X 往往是从那个对象算出来的。**

于是"对象差异""X 的取值""结果差异"三者同向变化,你看到一条漂亮的单调关系,却分不出谁是因。

实测过的一个例子:三个骨架比例不同 → 各自算出的缩放因子不同 → 残差随"缩放偏离 1 的程度"单调递增。据此报了"两边缩放语义不等价"。**结论是错的** —— 真因是那个缩放 op 本身在重复缩放,跟对象比例无关。

**拆法:固定一个,只变另一个。**
- 固定对象,**手动**扫参数取值 → 看参数本身的影响
- 固定参数,换对象 → 看对象的影响

那次拆开靠的是两个证据:固定对象扫参数时,残差在"不缩放"处取最小、向两侧增长;而**两个差异很大的对象,曲线逐点重合**。前者说明参数本身是主因,后者说明对象无关。

> 一条附带的:**对照组要真的是对照组**。同一次比较里若某个样本的参数取值**恰好等于**对照值,它只差浮点噪声,不能算进"A 比 B 好"的计数 —— 那是虚增证据。实测踩过:报"12 个组合全部改善",其中 4 个是同值对照。

## 两条数值判据

**① 自证的阈值要给浮点噪声留余量。** 判"两个输出是否相同"时,阈值卡太紧会得出反向结论。实测:用四元数夹角判等价,阈值卡 `1e-9`,而 `acos` 在 `dot ≈ 1` 附近数值敏感,同一个输出也会报出 `2.958e-6` 度的假差异 → 差点判成"有差异"(实际 `np.allclose(atol=0, rtol=0)` 为真)。**位置类给 1e-6,角度类给 1e-4,或者直接用位级比较。**

**② 数量级不合理时,先查场景,再读含义。** 荒谬的数字是**场景缺陷的信号**,不是待解释的现象。两个实例:一次"因果探测"报出 20926 cm / 31725 cm 的位移(实为求解发散——没有任何约束把对象固定住);一次"够不到的目标"却报 0 误差(实为漏给约束目标位置,整个对象被拽飞了,于是"够到"了远超它能力的目标)。

后者尤其值得记:**"不该成立的事情成立了"跟"该成立的事情不成立"一样是 bug 信号**,但前者更容易被当成好消息放过去。

## 优先找"不是你写的判官"

黑箱刻画里有两个特别便宜的 oracle,值得先找一遍再动手做因果实验:

**① 厂商自己的返回值 / 校验消息。** 很多 setter 返回 bool 表示"索引合法否",很多校验函数在失败时把阈值写进错误消息。这些是**厂商实施的一部分**,不受你的假设影响。
- 实例:用 setter 的返回值枚举出每个容器的**真实槽数**(比读文档可靠);从校验的错误消息原文里恢复出两个**取不到的内部阈值**(`Should be below 2.00000`),零反汇编。
- 推论:**凡是"校验会拒绝"的量,都能靠黑箱二分反推出来** —— 不需要读实施。

**② 库自己填好的对应关系,别做因果实验去猜。** 若库提供"按当前状态初始化一个集合"的函数,那它填出来的内容**就是**你想知道的映射。
- 实例:要搞清"effector 索引 ↔ 骨骼元素"的对应关系,第一版做的是"逐个驱动、看谁动最多"的因果实验 → 求解发散、数据废掉;后来发现有个 `...SetFromX()` 函数会按状态填好整个集合,**直接读回位置跟各元素比对,全部距离 0.0000**,映射一目了然。
- 判据:**因果实验(扰动→观测)比直接读回贵得多也脆得多**。先问"这个信息有没有被库自己暴露出来"。

## Anti-Patterns

| 反 pattern | 为什么错 | 修法 |
|---|---|---|
| 扫了没反应就记「这个参数没用」 | 五种原因里只有一种是真没用 | 五种逐一枚举再下结论 |
| 拿几组不同对象去比,推参数的影响 | 参数常是从对象算出来的,三者同向 | 固定对象手动扫参数 |
| 判等价的阈值卡到浮点极限 | 同一个输出也会报出假差异 → 反向结论 | 位置 1e-6 / 角度 1e-4 / 或位级比较 |
| 拿到荒谬量级的数字,去解释它 | 那是场景缺陷的信号 | 先查场景,再读含义 |
| 直接上因果实验(扰动→观测) | 贵、脆、容易发散 | 先找厂商返回值 / 库自己填的对应关系 |
| 同值样本算进「A 比 B 好」的计数 | 虚增证据 | 对照组要真的是对照组 |

## 诚实的边界

**这一整套目前只在一个项目上验证过**(逆向刻画一个闭源 IK 库的参数语义),其中"扫了没反应的五种原因"在该项目内有 **5 次独立复现**、每次真因不同。**未跨项目验证**,不满足 [`../guidelines/workflow/knowledge-promotion.md`](../guidelines/workflow/knowledge-promotion.md) 的两击规则 —— 按 apply-and-refine 用,第二个项目命中后再固化。

内容本身框架无关(没有任何一条依赖具体 SDK),但"框架无关"是设计意图,不是已验证的事实。
