# 先取证再修:调试不靠猜

## 核心规则

遇到 bug / 测试失败 / 非预期行为时,**不要凭假设直接改代码**。先用**证据确认根因**,再动手修。

"我觉得是 X → 直接改 X" 是反 pattern。改一个未经证实的假设,常常:**修错地方** / **掩盖症状**(症状偶然消失但根因还在)/ **引入新问题** / **烧光 failure budget**(见 [`../workflow/agent-lifecycle.md`](../workflow/agent-lifecycle.md) 失败升级)。

这条是 [`validation.md`](validation.md) 的**前置对称面**:validation 管"改完怎么验证",本条管"**改之前怎么确认根因**"。

## 取证手段(动手修之前)

- **加诊断日志**:在关键决策点 dump 状态——变量值、分支走向、**是否进入某代码路径**、对象/容器计数、指针有效性。
- **dump 数据结构**:打印 size、关键字段、id 映射。
- **断点 / 调试器**:单步、看调用栈、看实际值。
- **最小复现**:隔离到最小场景,排除干扰变量。
- **bisect**:二分(git bisect / 逐段注释)定位引入点。
- **读框架源码**:行为诡异且涉及外部框架时,读那一层源码确认 hidden contract(配合 reference-engine-source 类 skill)。

**关键判据**:你加的 log/dump 应该能**区分相互竞争的假设**——让"是 A 还是 B"有明确答案,而不只是"看起来对"。设计取证手段时先问:"这条证据出现/不出现,分别证明了什么?"

## 框架的校验器只能看它面前的局部,所以上游的错会伪装成局部的抱怨

一条关于**从哪里开始查**的判据:框架自带的校验 / 警告只能检查它手上那份数据的局部性质,**它没有"上游"这个概念**。所以一个上游数据错误传到它面前时,它报出来的是**局部几何 / 局部结构不对** —— 而那个报告**指向你的本地代码**。

实测形态:一个重定向框架报"髋部没朝向 +Z 轴 / 手臂不平行于 X 轴",两条都指向"骨架是怎么建的",差一步就去改建骨代码的朝向。**真因在上游**:数据是按另一个引擎的左手坐标系烘的,右手接收端直读得到镜像骨架 —— 而校验器看到的只是"这个姿势不对",它无从知道姿势为什么不对。

⇒ **收到框架告警时,先分清它在报"症状所在层"还是"根因所在层"**。校验器几乎总是前者。别把它的报告当定位结论用。

### 打破平局要用**方向性 oracle**,不是肉眼

上面那个例子里,"骨架摆姿不对"和"上游数据镜像了"两个假设**在画面上很难分辨**(镜像骨架看起来仍然是个正常的人形)。打破平局的是一条端到端的**符号断言**:

> 在源端推一个**已知符号**的位移,量目标端的符号。

实测结果:源端左手 **+40.3 cm**,目标端左手 **−36.2 cm** —— **符号反了**。这一条数字同时排除了"建骨朝向错"(那不会让方向反转)并锁定了手性问题。

这属于 [`../../techniques/adversarial-verification.md`](../../techniques/adversarial-verification.md) oracle 阶梯里的 **metamorphic 不变量**档:断言的是**关系**(输入方向 → 输出方向应同号),不是具体数值,所以不需要期望值表、也不需要参照实现。**任何"一条变换链"都适用**(重定向 / 坐标转换 / 单位换算 / 编解码链):先问一句"我这条链的方向性有没有被验过"。

> 顺带一条域事实(镜像修法):跨手性传骨骼动画时,修法是**一致的基变换**——静止几何偏移与流数据同时施加同一个反射(某轴取反 + 四元数对应分量取反,即 `M·R·M` 共轭)。⚠️ **前提是骨架左右对称**;不对称的 rig 这招不成立,这个前提必须跟公式一起写出来。

## 确认后再修

- 证据收敛到**单一确认根因**后才写 fix。
- fix 后**再取证**,确认确实是那个根因被解决(不是症状被偶然掩盖)。
- 诊断日志在确认 fix 生效**之前不要删**(见 [`../../techniques/adversarial-verification.md`](../../techniques/adversarial-verification.md) "Diagnostic Log Discipline")。

## Agent 自己观察不到时,让 user 协助取证

很多证据 agent 直接拿不到(GUI / 编辑器交互、运行期画面、硬件、远程环境)。这时**仍然不要猜**,而是把取证**外包给 user**:

1. 给 user **精准的 instrumentation**:具体加哪几条 log / dump 什么 / 跑哪几步操作。
2. 给一张 **"观察 → 含义" 解读表**,让 user 回报的证据能直接定位到环节。
3. user 回报证据后**再下结论 + 修**。

解读表示例(把"可能的观察"预先映射到"问题在哪一环"):

| 观察(log/现象) | 说明 | 下一步 |
|---|---|---|
| `X = NULL`(初始化处) | 初始化时序问题 | 改时序 / 延迟初始化 |
| 回调日志从不出现 | 回调没注册 / 没触发 | 查注册路径 |
| `count = 0` | 数据没填进来 | 查数据来源 |
| `count = N` 但无可见效果 | 下游(应用/绘制)问题 | 查下游 |

这比"你再试试 / 再看看"高效得多——一次往返就能定位,不浪费 user 时间。

### 反方向的一手取证:问"你刚才做了什么操作"

上面是**向前**下探针(你去跑这几步 / 加这几条 log)。还有一个**向后**的方向常被漏掉:**交互式工具的 bug,复现条件常常只存在于用户的操作史里,日志里根本没有。** 日志记的是结果(错误、状态),不记"这个人五分钟前在界面上点了什么"。

⇒ 遇到"某个操作之后就坏了 / 偶发坏了"的现象,**直接问用户做过什么操作**,把它当一等取证手段,不要只在日志里找。

实测形态:一个下游订阅方的数据流永久失效,日志只有一条格式错误、没有任何操作痕迹。真因是用户**在流送过程中切换了一个流类型开关** —— 这个信息不在任何日志里,是用户自己说的;拿到它之后才能去源码里确认机制(同名原地换定义、不注销旧的)并给出规避纪律。

## 一份文档 / 文件"打不开"时,你的代码可能就跑在加载器里

一个特殊但高频的形态:宿主(编辑器 / DCC / IDE)打不开一份文档,而**你写的插件恰好跑在那个加载流程里**。这时"文件坏了"是个**极容易接受又极贵**的判断。

机制:**插件的启用状态会被宿主文档序列化。** 宿主重新打开文档时恢复那个状态,于是插件的启动逻辑(可能含阻塞式握手、建对象、起线程)在**加载中途**、宿主处于半初始化状态时跑起来 —— 表现就是"打开到一半卡住"。

- **修法(插件侧)**:加**加载期守卫** —— 监听宿主的"加载开始 / 加载结束"事件,加载期间强制停用,启动入口早退。
- **取证手段**:用**格式自己的 SDK 直读**那份文件,绕开宿主。读通了就同时得到两个结论:文件没坏、问题在你的代码里。这是一个**独立于宿主的 oracle**。
- **归错代价**:见 [`reporting-limits-and-null-results.md`](reporting-limits-and-null-results.md) 规则 1 ——"用户的产物坏了"这个方向的下一步动作是**丢弃或重做**,而且丢掉不报错。**你的代码跑在读取路径里时,你是嫌疑人,不是旁观者。**

## Anti-Patterns

| 反 pattern | 为什么错 |
|---|---|
| "八成是 X,直接改 X" | 假设未证实;根因可能在别处,改了白改还可能引入新问题 |
| 连续试多个 speculative fix | 每个都没取证;改对了不知为何,改错了 budget 烧光(对应 agent-lifecycle 失败升级"换 layer 不是换 API"——但换之前要先取证知道卡在哪层) |
| 过早删诊断日志 | fix 没确认就删,错了要重加 |
| 让 user 反复"再试试"却不给精准 instrumentation | 浪费 user 时间;拿不到能定位的证据 |
| 把"代码看着对"当证据 | reading ≠ evidence(见 validation.md "Adversarial Mindset") |
| 把框架校验器的告警当定位结论 | 它只能看它面前的局部,上游的错会伪装成局部几何/结构不对,报告指向你的本地代码 |
| 只在日志里找交互式 bug 的复现条件 | 操作史不落日志;"你刚才点了什么"往往是唯一线索 |
| 宿主打不开文件就先怀疑文件 | 你的插件可能就跑在加载器里 —— 先自查自己这层,再用格式 SDK 直读作独立判据 |
| 用画面 / 肉眼判一条变换链的方向性 | 镜像后的结果看起来仍然正常;要用符号断言(推已知方向,量输出符号) |

## 项目实例

UE curvenet 插件 M3:viewport 控制点手柄不显示。Agent 第一反应是"八成是 `GUnrealEd` 在 `StartupModule` 时为 null 导致 component visualizer 没注册",准备直接改成 `OnPostEngineInit` 延迟注册。user 叫停:**先加 log 取证**——StartupModule 时 GUnrealEd 是否 valid / 注册是否跑 / `DrawVisualization` 是否被调 / 控制点数——确认到底卡在**注册、调用、数据、还是绘制**哪一环,再修。避免了对未证实假设的盲改(那个假设只是 4 个候选环节之一)。
