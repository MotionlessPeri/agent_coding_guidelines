# 自定义渲染效果：先选接入位置，再确定实现

**综合结论**：先把效果需要的数据和发生阶段说清，再选择能满足它的最外层接入方式。能在可用后处理位置用材质表达，就把后处理材质列为候选；需要 C++ 或自定义 Pass 时评估扩展点；已有具体限制证据表明材质和扩展接口无法满足需求时，再评估改引擎。修改既有 Pass 内部行为是原资料给出的典型例子，不是改引擎的唯一允许情形。这是对问题路由与扩展点资料的综合，不是按固定顺序跑完三种实现。[问题路由 §3.3](../card-09-scenario-mapping.md#33-想要特殊渲染效果)、[扩展路径 §1、§7](../card-12-pipeline-extension.md#1-三条路的选择)

## 当前依据与边界

原资料以 UE 5.8.0 / CL 55116800 为基准；扩展点卡片自述其 hook 签名、枚举与注册 API 来自该版本源码。本页只综合了这份记录，未重新核对源码或运行效果。具体调用前仍须核对目标分支、渲染路径及原章节；目标不是该版本时，按[版本与证据页](answering-with-version-and-evidence.md)判断能回答到哪里。[资料范围](../README.md)、[扩展点验证说明](../card-12-pipeline-extension.md)

## 把三个问题合并成一次选择

| 要判断的事 | 为什么会改变选择 | 来源 |
|---|---|---|
| 是增加效果，还是修改已有 Pass 的内部算法或数据布局？ | 后一种需求可能超出在既有阶段之间增加处理的能力，需要单独证明扩展点的限制 | [扩展点 §6](../card-12-pipeline-extension.md#6-改引擎的代价与纪律) |
| 需要什么输入，输出要在哪个阶段参与后续渲染？ | “加一个 Pass”不足以选位置；原资料分别讨论 GBuffer、scene color、半透明之后等情况 | [扩展点 §7](../card-12-pipeline-extension.md#7-选点决策树) |
| 目标版本、平台和当前分支是什么？ | 路由资料要求确认版本与平台；扩展点资料区分延迟和移动端入口，不能从桌面路径推定移动端同样工作 | [项目背景 §4](../card-09-scenario-mapping.md#4-接手新项目先问什么)、[扩展点 §2.2](../card-12-pipeline-extension.md#22-render-thread渲染阶段拿-frdgbuilder) |

这些问题用于补齐当前决定缺少的信息；项目已有有效答案时直接复用，不新增逐项审批。

## 三条候选路线

| 路线 | 本资料支持何时考虑它 | 还不能省掉什么 |
|---|---|---|
| 后处理材质 | 效果可用材质表达，并且某个可用插入位置满足输入、输出阶段要求 | 在目标版本核对位置与输入含义；不能只凭“后处理”三个字选枚举 |
| `ISceneViewExtension` 等现有扩展点 | 需要 C++ 或自定义 Pass，并能在现有回调阶段获得所需数据 | 核对具体回调、线程、渲染路径与生命周期；不能把所有回调当作同一种 RDG 接口 |
| 改引擎 | 已有具体限制证据说明材质和现有扩展接口不能满足需求；修改既有 Pass 内部行为是例子 | 说明限制证据、修改范围及上游升级维护成本 |

这张表综合 [扩展点 §1–7](../card-12-pipeline-extension.md) 的选择、接口和维护条件；它没有承诺扩展点适合所有自定义效果，也没有把改引擎视为自动获批的动作。

**RDG 与接入路线不是同一层选择。** 上表决定在哪个现有阶段或接口接入；RDG 用于组织渲染 Pass 及其资源依赖，可以在提供相应接口的扩展点内使用。因此“用 RDG”和“用扩展点”并不互斥，也不能仅因要写 RDG Pass 就推定必须改引擎。实际回调是否提供合适接口仍要核对，具体 API 签名不由本页担保。[扩展点 §2.2 及关联说明](../card-12-pipeline-extension.md#22-render-thread渲染阶段拿-frdgbuilder)、[RDG 概述](../card-08-rdg.md#概述)

## 两个具体问题怎样回答

**“只想对最终画面做一个可用材质表达的效果，要先改引擎吗？”**

可以先把后处理材质列为候选，核对目标版本有没有满足输入和阶段要求的位置。若位置不满足，再看扩展点是否提供所需阶段；当前信息不足以证明需要改引擎。原资料的具体位置和输入说明在[扩展点 §4、§5](../card-12-pipeline-extension.md#4-订阅后处理链)。这里给出的是候选路线，不是效果已经可实现或验证通过的结论。

**“需要读 GBuffer 做自定义计算，PC 和移动端都要支持，能抄一个回调吗？”**

先将现有扩展点作为候选；原资料分别列出延迟渲染与移动端 BasePass 之后的入口，且两者参数接口不同。因此需要按两个目标路径核对数据可见性和回调形式，不能拿一个桌面示例直接承诺双端支持。[扩展点 §2.2](../card-12-pipeline-extension.md#22-render-thread渲染阶段拿-frdgbuilder)

确定接入点后，再查当前版本中需要的 RDG 用法。RDG 卡片开头明确说其他章节的 API 签名未逐条核验，所以不能将其中模板直接当作已验证代码。[RDG 验证说明](../card-08-rdg.md)、[怎样带着证据边界回答](answering-with-version-and-evidence.md)

## 从候选路线到实现前的证据

阅读目标版本相关声明、调用者和所需输入条件；接口名称存在只是第一步。若找不到资料，先检查源码分发是否完整、符号是否由宏生成，以及查询范围；搜索无结果不能单独证明引擎不支持。[本机核证 §1、§7](../card-13-verify-locally.md#7-校验方法自身的盲区)

本页没有提供可直接执行的实现或 API 兼容保证。需要跨版本结论或原资料有部分未核内容时，继续读[按版本与证据回答](answering-with-version-and-evidence.md)；来源位置与更新依赖见 [sources.json](sources.json)。
