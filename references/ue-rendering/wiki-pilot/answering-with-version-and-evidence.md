# UE 渲染资料：按版本与证据回答

**综合结论**：候选方案、接口名称存在、签名符合目标版本，以及运行行为正确，是不同层次的结论。现有资料可帮助选[渲染扩展路线](choosing-custom-rendering-route.md)，但回答的确定程度要受相关章节的证据限制；不能因为其中一部分核对过，就给整套方案盖上“已验证”。[资料引用纪律](../README.md#引用纪律)、[RDG 验证说明](../card-08-rdg.md)、[核证范围](../card-13-verify-locally.md)

## 三个具体问题怎样回答

**“RDG 卡片检查过 CVar，我能直接照抄它的函数签名吗？”**

不能据此认定签名已经核验。该卡片开头明确限定了核对范围，其他 API 签名仍需对照目标版本头文件。可以先用文档定位概念和候选用法，再核对实际要调用的接口；这不要求把整份 RDG 卡片重新验证一遍。[RDG 验证说明](../card-08-rdg.md)

**“我们的项目是另一个版本，你能保证刚选的渲染扩展路线和 API 不变吗？”**

只能先给出以这套 5.8.0 资料为依据的候选路线，不能保证另一版本兼容。若能访问目标版本，核对涉及的接口及调用路径；若暂时不能核对，明确保留该缺口，不把资料中的核对写成自己刚完成的验证。先确认目标小版本、分支与平台，再使用[路线页](choosing-custom-rendering-route.md)所需的具体接口。[项目背景 §4](../card-09-scenario-mapping.md#4-接手新项目先问什么)、[跨版本核证 §6](../card-13-verify-locally.md#6-确认某特性在客户版本存不存在)

**“目标源码里搜不到这个名字，是不是引擎已经不支持？”**

当前结果只支持“这次搜索没有定位到”。原核证资料列出源码目录被裁剪、解析器未覆盖注册形式、宏生成名称和缺平台代码等盲区，应先检查这些可能性，并使用已知存在的对象检验搜索方法。即使找到了名字，也还要读声明和使用处，不能只靠一次文本命中确认行为。[检查盲区 §7](../card-13-verify-locally.md#7-校验方法自身的盲区)、[消费路径 §4](../card-13-verify-locally.md#4-从-cvar-反查生效路径)

## 回答里保留的最小证据

围绕当前结论说明：依据哪份来源及其版本、来源实际核过哪一部分、当前项目还有什么未确认，以及下一步如何确认。不要把文件更新日期当作引擎验证日期，也不要把本页的综合日期当作来源新增证据。

例如可以说：“这套资料在 5.8.0 的扩展点记录中提供了候选入口；你们的目标分支尚未核对，因此目前只能给选型建议，不能提供接口兼容保证。”如果当前项目已有覆盖同一路径的有效证据，则引用它并说明范围，不重复声称未知。

来源修订、撤回核验声明或新增相反证据时，需要重新检查上表及这些答复。维护者实际读取差异并更新对应结论，不能只刷新文件哈希。依赖快照与人工更新方法见 [README](README.md) 和 [sources.json](sources.json)。
