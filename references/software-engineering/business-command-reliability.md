# 业务命令的提交、外部副作用与失败恢复

业务命令改变的是一组需要同时成立的事实。可靠性取决于提交点是否明确，以及失败、重复调用和重启后这些事实是否仍然一致。
本页适用于同时涉及持久数据、进程内资源或外部服务的业务操作；它提供判断依据，不规定采用工作流引擎、分布式事务或新增公共状态。
资料读取日期：2026-10-17。下文示例是机制推演，不是某个产品的运行验收。

## 先明确一次命令承诺什么

以“把工作分配给执行者”为例，有意义的不变量是“每项进行中的工作有唯一执行者，执行者的当前占用指向同一项工作”。只把工作状态改为 `running`，不能代表分配已经完成。
命令的前置条件、允许改变的事实和提交点决定其原子边界；接口函数的起止位置不一定就是这个边界。
如果这些事实由同一数据库拥有，可以在一个短事务内重验条件、更新关联记录并提交。SQLite 的原子性保证针对同一事务内的数据变化，不覆盖任意文件、网络请求或内存对象。[SQLite 事务说明](https://www.sqlite.org/transactional.html)

并发下的“先查可用、再写占用”需要数据库实际执行的保护，例如唯一约束、条件更新、适当的锁或隔离级别。
事务存在并不自动证明业务不变量成立；PostgreSQL 不同隔离级别允许的现象不同，串行化失败也要求重新执行完整事务及决定其写入的逻辑。[PostgreSQL 18 事务隔离](https://www.postgresql.org/docs/18/transaction-iso.html)
若更新依赖先前读到的版本，条件不再成立时就重新判定业务请求，不能把旧决策照写进去。

将提交前后的含义分清，有助于避免错误的失败处理：

| 观察 | 能作出的判断 | 恢复依据 |
|---|---|---|
| 已确认本地事务未提交 | 该事务的业务变化没有生效 | 原有持久事实；另查事务外准备资源 |
| 已确认本地事务提交，后续通知失败 | 本地业务事实已经生效 | 原业务身份和未完成的后续动作 |
| 调用超时或响应断线，提交与否未知 | 调用方没有拿到确定结果 | 用原操作身份查询或按幂等契约重试 |

这三种情况不必成为三个公共枚举值；现有错误结果、查询接口和持久记录能准确表达时即可复用。

## 跨进程调用：超时不等于没有发生

外部服务可能已经创建资源，只是响应没有到达。超时限制的是等待时间，不能撤销已发生的副作用；同机子进程也可能出现这一间隙。[AWS 超时与重试](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)
因此，结果未知时换一个请求标识重新创建，可能得到两份资源。先利用原请求身份查结果，或沿外部接口承诺的幂等方式重试；外部接口没有这种能力时，明确保留不确定性及可执行的核对方式。

幂等键标识一次业务意图，同一意图的重试沿用同一键；用户另一次合法创建使用新键，即使参数完全相同。
键的作用域、同键不同参数的处理、保存期限和结果返回方式属于接口语义。仅按请求正文哈希去重，无法区分“重试创建”和“确实要第二份”。
对本地可事务化的修改，去重记录与业务修改共同提交，才能避免“已记处理却没生效”或“已生效却没记处理”。外部副作用仍受外部接口能力限制。[AWS 幂等 API](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

只有需要保证“提交后最终发出通知”，且已有记录不能支持重放时，才评估事务内保存待发送事实，例如 `outbox`。
它把业务变化和发送意图一同保存，发送在提交后进行；发送成功但确认前崩溃仍可能造成重复，所以接收方依然需要按事件身份处理重复。它不使任意外部动作自动获得恰好一次语义。[AWS 事务型 outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

重试应针对可恢复的错误，并受总截止时间或次数约束；并发客户较多时用退避和随机抖动分散压力。
调用栈多层各自重试会放大请求量，宜在明确的一层负责重试，并计入下层 SDK 已有行为。确定的参数或业务条件错误需要改变条件，重复原请求通常无益。[AWS 超时与重试](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)

## 恢复以已经提交的事实为起点

长操作可以由多个短的原子动作构成，动作之间保存足够的稳定身份和进度，使下一次执行知道哪些事实已成立、哪些动作尚未完成。
这可以是已有任务、资源或投递记录，不必另建通用执行平台。持久化信息的价值在于能支持实际恢复决策。

例如，先准备一个暂不执行工作的资源，再提交业务绑定，最后发送启动输入：

| 失败位置 | 合理的业务含义 | 后续处理示例 |
|---|---|---|
| 资源准备失败，业务提交尚未发生 | 原业务关系保持不变 | 释放本次拥有的临时资源 |
| 业务绑定已提交，启动输入发送失败 | 绑定仍成立，启动尚待完成 | 按原绑定恢复，避免重新分配 |
| 输入已接收，确认丢失 | 输入是否处理不能从断线判断 | 按输入身份查询或去重重放 |

这里的业务提交可以是原子的，整个异步调用仍不是“出错就完全没有发生”。进程在提交前崩溃也可能留下事务外文件，需要按准确身份核对，不能仅因业务未提交就假定它们不存在。

补偿是新的业务动作，例如退回已预留的库存；它与数据库回滚不同。
直接恢复旧快照可能覆盖其他并发修改；补偿需要按当前事实和业务规则执行，且补偿本身可能失败并需要继续。无法撤销的动作应在承诺前识别，而不是给它包装一个名为 `rollback` 的函数。[Microsoft 补偿事务](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)
能够通过简单重试恢复的操作，不因存在失败就必须采用补偿体系。

## 业务终态、资源停止与再次可用是不同事实

工作已写入完成结果，并不证明进程、回调、锁或执行位置已经释放。
有状态资源应有明确所有者和释放条件：正常完成、失败、取消、启动中断各自最终由谁收尾，以及释放失败怎样被看到。
内存中的“可用”集合若由持久绑定派生，就需要明确失效和重建办法；进程重启不能凭空把仍有业务责任的资源当成空闲。
相关数据归属见[双层数据模型](../../guidelines/code/dual-layer-data-ownership.md)；是否能够整体重建取决于权威数据是否足够，不照搬编辑器的刷新策略。

一个典型并发错误：旧工作 A 已结束，资源分给 B；A 的晚到回调再执行“清空当前占用”，把 B 清掉。
处理这类回调时，将动作限定到原工作的身份或版本，例如“仅当当前占用仍为 A 才释放”；检查和改变应在同一受保护操作里完成。
同样，取消请求只表达停止意图，不能当作工作已经静止的证据。旧执行仍能写入时，释放占用并立刻交给新执行可能造成双写。
等待资源停止也需要明确的失败出口；超出等待预算后仍未确认停止，就报告准确的未释放资源与可执行处置，不能把超时当成已释放。
这些是从所有权和并发不变量推导的设计例子，具体使用锁、条件更新还是现有运行代次，由当前系统决定。

恢复既要避免损坏既有结果，也要恢复后续可用性。只查询到 `finished`，尚不能证明执行者可以接受下一项工作。

## 日志要回答“哪次操作卡在哪个阶段”

一条“启动失败”难以判断失败发生在提交前还是提交后。围绕具体诊断问题记录少量关联事实更有用：

| 要回答的问题 | 可记录的事实示例 |
|---|---|
| 这几条日志属于同一业务意图吗？ | 稳定操作 ID、目标资源 ID、单次尝试 ID |
| 哪一步已经成立？ | 阶段、提交确认、外部请求或回执 ID |
| 为什么不能继续？ | 原始错误类别、超时或取消原因、重试次数与截止时间 |
| 旧执行是否仍占资源？ | 原所有者与当前所有者、释放开始及完成、清理失败 |

OpenTelemetry 提供 `TraceId`、`SpanId`、事件时间、观察时间和 `Attributes` 等关联字段；业务操作 ID 与恢复阶段仍需应用自行定义。[OpenTelemetry 日志模型](https://opentelemetry.io/docs/specs/otel/logs/data-model/)
稳定业务身份应能跨重试与重启关联；一次请求的追踪 ID 不必等同于该业务身份。无需为此默认安装新的观测平台。
日志可能缓冲、丢失或采样，所以缺一条成功日志不能证明没有提交。判定业务事实仍以相应权威记录或公开查询结果为准。
记录标识、阶段和安全的错误摘要，通常不需要保存用户正文或认证信息；保留原始业务错误和清理错误各自的含义。

## 从公开入口验证承诺

下面是按故障位置选择的行为样例，不是所有改动都要执行的固定套件。测试方法沿用[验证](../../guidelines/code/validation.md)和[测试目的](../../guidelines/code/test-purpose.md)。
通过实际调用者可使用的命令和查询观察结果；故障可注入在外部适配器或提交后响应通道，避免用私有方法直接写出期望状态。

| 场景 | 可观察验收 |
|---|---|
| 正常成功 | 查询到完整关联事实，重复读取稳定；必要的外部效果存在 |
| 提交前明确失败 | 公开查询仍为原有效状态，没有半份绑定；本次准备资源按契约释放或可核对 |
| 提交后响应断线 | 按原操作身份找回结果；安全重试不产生第二份业务效果 |
| 提交后通知失败并重启 | 重启后保留原业务身份；能够继续未完成动作，重复送达不破坏结果 |
| 两个请求争用同一资源 | 最终至多一个有效占用，失败方得到可解释的结果 |
| 旧回调在新工作开始后到达 | 新工作关系和结果保持有效，旧回调不能清掉新占用 |
| 一项工作失败或完成后继续下一项 | 下一项从正常入口被接受并实际推进；既有结果保持，释放失败能被定位 |

用这些观察区分正确性与可用性：不重复、不丢业务事实是正确性；故障后仍能推进是可用性。两者缺一都可能让用户流程失效。
这类用例证明的是指定版本、故障位置和环境中的行为；通过受控故障注入不等于已经定位历史现场故障。

## 来源核对与适用限制

2026-10-17 核对上述第一方资料。数据库原子性、隔离级别、重试与补偿的来源结论只在各自契约内成立；字段组合、晚到回调和表中业务例子属于本文的机制推演，没有运行产品或示例代码。

| 来源 | 本页采用的部分 | 版本或限制 |
|---|---|---|
| SQLite 事务说明 | 同一事务内的数据变化原子提交 | 不代替目标系统的存储配置与崩溃验收，不覆盖事务外副作用 |
| PostgreSQL 事务隔离 | 隔离级别的差异与完整事务重试 | 正文固定到 18 文档；实施仍按目标版本核对，不默认提高所有事务的隔离级别 |
| AWS 幂等 API | 请求身份、重复意图与原子去重 | 云服务案例不构成其他接口的契约，不承诺无限期去重 |
| AWS 超时、重试与抖动 | 不确定结果、有限重试和重试放大 | 时间参数须来自实际延迟、调用成本和现有 SDK 行为，不照搬示例数值 |
| AWS 事务型 outbox | 业务变化与待发送事实共同提交 | 仅用于实际双写问题；重复处理仍需按语义验证，不推导任意外部效果恰好一次 |
| Microsoft 补偿事务 | 业务补偿与数据库回滚不同 | 不默认引入 Saga、补偿平台或新的工作流产品 |
| OpenTelemetry 日志模型 | 追踪关联、事件与观察时间、属性 | 字段语义不保证日志送达，也不替应用定义稳定业务身份；本页不依赖特定 SDK 版本 |

本页不将原子性解释为整个异步调用必须统一回滚，也不将恢复例子中的内部资源准备提升为暂停/放行等公共产品语义。是否增加持久记录或恢复动作，仍由实际业务承诺和已有能力决定。
