# 范围审查与执行入口

防止擅自增加需求，需要分别回答两个问题：候选改动是否符合原始要求，以及未经有效审查的候选能否进入正式交付。前者需要判断；后者可以在选定入口实施机械限制。流程引擎不能仅凭一个 `approved` 字段证明二者都成立。

本文是机制比较与试点建议，不启用工具、改变权限或增加通用审批点。范围规范见[代码约束](../../guidelines/code/constraints.md#plan-scope-integrity)，审查方法见[代码审查](../../guidelines/workflow/code-review.md#scope-and-independent-review-evidence)。现有授权内的普通修复继续自主完成；新增产品语义需要回到用户要求判断，不按代码行数或状态变量数量机械裁决。

## 判断依据与受审对象

审查者先读用户原始要求、后续明确决定、排除项和已有可用能力，再独立判断最小必要行为。作者整理的方案用于解释实现，不能取代这些来源。如果新增约束本来就来自作者，再以满足该约束证明新机制不可删除，删除检验已经偏离了用户请求。

审查对象是实际候选 diff 及受影响调用路径。既检查额外行为，也检查必须保留的业务约束；“删除更多”本身不代表范围正确。测试用于验证行为，但作者新增的测试不会自动成为用户验收要求。

现有审查记录只需能定位需求依据、被比较的基线、候选版本和具体结论，不必另造表格或 JSON 协议。未提交候选应覆盖实际待集成文件；只记录 `HEAD` 无法代表工作区改动。版本对应关系和审查来源是不同问题，同一作者填写的哈希与通过字段不能同时证明两者。

## 三种机制分别能保护什么

| 选择 | 实际保护入口 | 判断和执行由谁承担 | 绕过边界与成本 |
|---|---|---|---|
| 现有独立对话审查，加候选目录与人工集成 | 集成人按纪律决定是否接受候选；同权限脚本只能约束经它调用的动作 | 独立审查者判断，集成人核对版本并操作 | 同一用户能直接写正式树、改脚本或使用集成凭据时，没有强制隔离；改动少，但依赖执行纪律 |
| 现有托管 Git 的受保护分支或已有独立集成器 | 拒绝不满足要求的受保护分支更新 | 独立审查者给出结论，服务端依据有效审查和检查结果接受或拒绝更新 | 需要正确配置权限、审查失效规则与可信结果来源；管理员、规则编辑权、旁路凭据和其他交付入口仍需核清 |
| Loom 等工作流引擎 | 引擎内部的阶段推进与恢复边界 | 引擎检查合同和结果；外部模型、用户或工具动作由调用方完成 | 若调用方能手填证据或绕开引擎直接集成，阶段成功不等于交付受控；另需维护模板、版本锁、适配和审计产物 |

Git 本地 `pre-commit` 可以被 `--no-verify` 跳过，hook 目录也由配置选择，因此不能把作者可修改的本地 hook 当作独立权限边界。服务端 `pre-receive` 可以拒绝接收更新，但若作者也能直接写服务器仓库或改 hook，仍不能保护该旁路。[Git hooks 文档](https://git-scm.com/docs/githooks)

GitHub 的必需审查、过期批准失效及最新推送审查可以约束受保护分支更新；必需检查还能限定来源 App。默认管理员旁路及审查驳回权限需要单独核对。项目是否具备相应套餐、身份和配置，本轮未核验，不能据此声称当前仓库已有保护。[GitHub 保护分支说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

上述 GitHub 选项是候选能力，不是通用配置清单。选择某个检查来源，也不自动保证其执行逻辑可信：仍须确认作者是否能修改判定代码、提供伪造输入或取得该身份。不同对话共用一个账号可以改善判断独立性，却不产生账号权限隔离。

## 最小试点建议

先只选择一个交付动作，例如将一个候选合入指定分支。列明谁能改变该分支、审查规则、判定代码和凭据，以及部署能否绕过它。优先复用已有受保护入口；若所有操作仍由同一无限制账号执行，先如实定位为纪律试点。建立新账号、权限隔离、服务或托管规则属于另一个待决定的接入范围。

实现者可以继续在隔离候选中工作；独立审查者从原始要求评估具体候选。只有被选定的集成入口才接受有效结果，并在实际写入时核对受审对象和当前基线，避免检查后换成另一份内容。若部署直接消费任意本地文件，保护 Git 分支并未覆盖部署，需要单独选择是否纳入该入口。

试点使用一个合法修复和一个未经同意新增生命周期的候选。期望审查结论由独立审查者预先确定，不由实现者修改标签使其通过。保留原始要求、实际 diff、真实入口返回和受保护目标前后状态；不要以生成了报告、状态变成 `done` 或返回布尔值作为动作已经被挡住的证明。

| 案例 | 预期判断或入口行为 | 要观察的结果 |
|---|---|---|
| 修复原始需求明确的错误，保留既有业务约束 | 独立审查接受，入口允许该候选 | 目标确实更新为受审候选，相关验收通过 |
| 作者以自行新增条件证明额外生命周期必要 | 独立审查指出来源缺失，入口拒绝未获所需授权的候选 | 目标保持原版本，原始要求未被作者自建条件替换 |
| 候选没有独立审查 | 入口拒绝 | 实际写入未发生 |
| 审查后修改候选，或基线变化影响结论 | 旧结果不足以放行变化部分 | 新版本无法沿用失效结论进入目标 |
| 作者只填 `approved`，或把自检标为独立审查 | 不能作为可信的独立判断来源 | 伪造结果被入口拒绝；若放行则记录机制失败 |
| 流程停在等待，但作者直接调用其他写入路径 | 依所声明边界检验旁路 | 能写入则明确报告该入口未被覆盖 |
| 删掉必要业务约束以获得更小 diff | 独立审查拒绝 | 精简不能以损害原始要求为代价 |

这些是待执行的验收案例，不是已通过的测试。若语义判断通过而旁路仍能更新目标，说明独立审查有作用但执行隔离不足；若入口拒绝缺失结果而审查者接受了越界候选，说明执行限制存在但范围判断失败。两类问题分别报告，不能互相替代。
