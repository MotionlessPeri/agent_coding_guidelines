# 注释参考

仅在审查发现注释或接口说明问题时读取。这里区分知识事实、项目风格和审查动作，不要求批量改写已有良好注释。

## 保留理由，消除临时依赖

代码附近应有理解当前行为所需的契约和设计理由。实现期的 Task、Phase、milestone 标签或会清理的计划文档可能失效；发现这类引用时，先提取它承载的理由，再决定删除或替换。

| 引用目标 | 判断 |
|---|---|
| 会清理的计划、临时任务编号、仅描述“从旧实现改来”的历史 | 不宜成为理解当前行为的必要前提；有用理由留在代码附近 |
| 论文、稳定规范、已提交的架构文档、框架源码 | 可以保留为深入阅读的来源；附近说明当前代码依赖的关键事实 |

不要求把长篇算法推导复制进每处注释。就地写清必要的假设、单位、所有权或不变式，完整论证可留在稳定来源中。删除噪音不能连同正确的理由一起删除。

例如，“防止输入已在 posed 空间时再次形变”解释当前行为；“Task 2.4 修改旧 deformer”只描述实施历史。前者应保留，后者是否需要由当前读者用途决定。

## 接口契约及可选的 Doxygen 格式

公共 API、跨模块入口或前置条件不明显的函数，可能需要说明参数含义、空间、单位、所有权、空值、返回值和失败行为。先看项目既有格式和类型系统已表达什么，再补缺失信息。

项目使用 Doxygen 时可以采用：

```cpp
/**
 * 拆分指定 spline 的一段；保持控制点池索引稳定。
 * @param splineIdx 要分裂的 spline 池索引
 * @param t 分裂参数，范围 [0, 1]
 * @return 新端点索引；参数越界时返回 -1，不修改数据
 */
int splitSpline(int splineIdx, double t);
```

示例中的返回值和边界只是示例函数的契约，不能套到其他 API。

- tag 应提供类型和参数名没有表达的信息。只写 `@param pos 位置` 通常没有价值。
- 签名自明的访问器、简单私有函数或框架样板不需要为了格式补空注释。
- 头文件声明处适合放消费方需要的契约；文件内 helper 可放定义处。
- 块注释与函数体里的原因说明不必重复。项目不用 Doxygen 时，普通注释也可表达同样信息。

## 行文规范与操作的边界

项目语言、术语和文体沿用已有约定。确实要判断散文或术语时，查规范仓根的 `guidelines/writing/prose-and-register.md`；确实要判断函数清晰度时，查 `guidelines/code/function-clarity.md`。这些引用是知识与规范来源，不要求启动额外写作或审查工作流。

上述路径相对项目 `AGENTS.md` 或 `CLAUDE.md` 指向的规范仓根，不相对本技能安装目录。
