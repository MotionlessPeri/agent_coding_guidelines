# 审查步骤

按当前阶段选用；已有且仍有效的结构说明、决策和验证结果不必重做。

## 确定范围和结构

先列任务所属的文件及职责，说明主要数据流或调用关系。少量局部改动通常用几句话足够；跨多个组件、入口和状态边界时，表格或图更便于检查遗漏。

需要逐函数覆盖时，列函数名、职责和关注点，重点标记公共 API、跨边界入口、非平凡前置条件及复杂控制流。行数可作为定位线索，不能仅因超过 50 或 80 行就判定需要重构；签名自明的访问器可合并说明。

跨会话审查应使用改动前记录的任务基线。不要用 `HEAD~1` 猜基线；基线或文件归属不明时先确认可达范围，再报告覆盖限制。

## 检查发现

| 方面 | 检查什么 | 如何处理 |
|---|---|---|
| 正确性 | 边界、退化输入、优先级、状态归属、调用顺序和接口契约 | 给出可定位证据；授权内必要修正直接处理 |
| 可读性 | 职责混杂、难追踪的控制流、重复逻辑是否会共同变化 | 说明具体维护代价；可选重构与必要修正分开 |
| 性能 | 热路径重复工作、昂贵调用、无效刷新 | 用测量支持性能结论；无证据时保留为待核假设 |
| 注释 | 契约缺失、理由过期、依赖临时文档、格式与项目不一致 | 有实际问题时查 [注释参考](comment-reference.md) |

发现写明位置、影响、证据和建议动作；不为凑齐分类制造问题。常见的结构拆法是把一个按输出或分支派发的大函数拆成各自职责明确的子函数，但只有它改善理解或修改边界时才值得做。

## 执行和验证

必要修正沿用任务授权。新增可选重构先说明具体收益、范围与风险，由用户选择；已有明确授权时不重复请求确认。

按实际改动选择证据：

| 改动 | 可用的验证 |
|---|---|
| 只改注释或文字 | 核对 diff、链接、示例及适用的文档检查；通常无需重建二进制 |
| 移动或拆分实现，要求行为不变 | 受影响行为的测试、关键输入前后对照，以及项目要求的构建检查 |
| 原生模块、DLL、插件的 ABI、生成文件或加载状态可能影响结果 | 按项目构建与加载契约决定是否需要干净重建和重新加载 |
| GUI、编辑器状态或人工判断是验收对象 | 对相应界面和状态进行可观察验证；编译不能替代该证据 |

既有证据的输入包括受影响源码、产物和环境。源码可用内容 hash 对照，产物和环境使用对应标识；不能只凭“之后没有提交”判断。单独的 `git diff` 看不到未跟踪文件、产物和环境，也不能用来证明所有输入未变。

只有输入或判据变化、失败或未解决问题使旧证据不足时才补验对应部分。未执行的检查标为未验证，不写成通过。

## 记录与交付

复用任务已有的 brief、worklog、计划或审查记录。只有持续跟踪或交接确实需要、且没有现成记录时才新建记录。

交付说明包含范围、重要发现、采取的动作、验证结果和剩余问题即可。用户要求完整表格、独立审查或指定格式时另行满足。

有提交授权时，结构重构和大批注释清理通常适合分主题提交，便于看清语义变化；小型必要注释可以随对应实现提交。不要仅为满足技能格式而制造提交或扩大修改范围。

## 一个结构判断示例
