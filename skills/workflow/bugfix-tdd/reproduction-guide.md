# 复现与回归

这是缺陷修复的操作参考。按当前阶段读取；已经取得且仍对应当前输入的证据可以复用。

## 选择复现方式

先看三个量：自动测试的搭建和清理成本、缺陷再次出现的风险、一次交互验证的成本。

| 情形 | 通常合适的方式 |
|---|---|
| 数据、算法、解析器、格式转换，输入输出可确定 | 自动测试，便于持续回归 |
| 常改的关键路径，自动与交互验证成本接近 | 自动测试 |
| 编辑器的拖拽、菜单、弹窗、视觉效果 | 能可靠观察的界面自动化或交互验证 |
| 创建资产、启动服务等准备远比验证昂贵，已有有效校验器 | 复用现有集成检查，或保留可复现的交互用例 |
| 改动跨共享接口或多个调用方 | 覆盖相关边界，不能仅按改动行数决定测试形式 |

不要为了凑覆盖率制造只服务于测试的中间层。优先测实际入口；确实需要重构以隔离依赖时，说明它对生产结构的价值和影响。

在已有任务记录或交付说明里简要记下选择及理由即可，不要求另建文档。用户要求先审测试方案时遵从该要求；已有授权覆盖时继续执行。

## 修复前：确认失败

1. 记录输入或 fixture、操作、期望结果和预期失败位置。
2. 运行复现，保留实际失败输出或可观察的错误状态。
3. 确认测试确实执行，失败不是缺少依赖、错误 fixture 或测试自身异常造成的。失败与预期不符时先查原因。
4. 检查断言能区分目标缺陷与正确行为；涉及多个已知表现时覆盖相应边界。

已有失败日志或用例只有在能追到缺陷版本、输入、环境和判据时才可替代重复复现。只有用户描述或代码推测时，不能说已经取得红测证据。

## 修复后：对照验证

1. 实施授权范围内解决该缺陷所需的改动，避免把邻近可选重构或其他缺陷混进来。
2. 使用同样的输入、操作和判据重跑，观察失败变为通过。
3. 检查实际输出和执行数量，防止测试发现配置错误导致“零测试通过”。
4. 按受影响行为及项目要求运行回归，记录检查范围和结果。

测试失败时先区分生产回归、测试假设错误和既有环境问题。可以修正确实错误的测试，但要保留理由，不能把它静默跳过后宣称通过。不相关的既有失败单列，不归到本次修复，也不隐瞒。

## 交互验证的可复现步骤

交互路径保留与自动测试相同的前后对照：

1. 记录初始状态、fixture、界面位置、输入和具体观察点。
2. 修复前按步骤执行并观察错误。
3. 修复后重新加载同一初始状态，执行相同步骤并观察结果。
4. 记录执行者、版本或产物标识、环境及证据位置。

执行者可以是 agent。用户只在需要主观视觉判断、人工验收或 agent 无法访问的环境中参与；缺少其中一次可靠观察时，明确报告验证缺口。

## 回归范围与交付

从缺陷入口向外检查受影响的共享状态、调用方、序列化或兼容性边界。局部实现已有充分检查时不强制全仓回归；公共接口、广泛共享代码或项目规定要求全套检查时应扩大范围。

交付说明写清缺陷表现、原因、修复前后证据、回归范围和未完成检查。测试与修复通常适合同一主题提交；若项目要求不同提交方式，保持关联和可复现性即可。仅在已有提交授权时执行提交。

新发现的独立缺陷或可选重构按原任务范围处理。不能仅因它在修复途中被发现，就扩大授权范围。
