# 修复证据的说明与示例

这些材料用于解释和选择证据，不是每次修复都要执行的额外阶段。

## 为什么要看修复前失败

绿测单独通过无法区分“修复有效”和“测试从未激发问题”。修复前失败的实际输出，能检查 fixture 和断言是否命中目标行为。失败来自导入错误、服务未启动或断言写错时，不构成目标缺陷的证据。

“精准命中根因”不要求测试绑定内部实现细节。优先选择能区分竞争解释、且未来实现变化后仍有意义的可观察行为。

## 一份可复用的记录

按任务需要保留以下信息，可放在现有用例、任务记录或交付说明中：

| 字段 | 内容 |
|---|---|
| 缺陷与范围 | 什么输入触发什么错误，哪些调用方受影响 |
| 初始状态 | fixture 路径、初始化步骤、依赖和环境 |
| 判据 | 可观察的期望行为及修复前实际行为 |
| 前后证据 | 命令或操作、版本或产物标识、输出或截图位置 |
| 回归 | 选择了哪些边界，结果如何 |
| 未验证部分 | 缺少什么证据，原因及仍不能确认的结论 |

fixture 应尽量小且能重新加载到同一状态。可复用的测试数据、资产或初始化脚本随对应用例保存；已有项目测试目录和格式优先。

## 性能缺陷

性能红测可以是基准加验收上限，但该上限必须来自当前需求，不能为了产生失败临时编造。使用相同输入、构建模式和环境；记录重复测量的分布，区分噪声与改进。计时不稳定时保留可复现步骤和前后读数，说明不确定性，不把一次最快结果当作修复证明。

## 复现困难

先检查输入是否有效、目标分支是否执行，再检查根因假设、外部依赖和环境。不要按固定分钟数放弃或自动改写问题。无法取得修复前证据时明确说明，继续能够独立完成的调查；不能把“未复现”写成“已验证修复”。

真实编辑器、外部服务、锁或线程调度可能使自动用例昂贵。交互或集成验证仍需可观察的判据与初始状态，而不是只写“看起来正常”。

## 修复经验与长期规则

一次修复的证据只支持其已覆盖范围，不自动证明普遍规则。当前修复与把经验写入长期规范是不同产物；只有正在提出长期规则时，才查规范仓根的 `guidelines/workflow/knowledge-promotion.md`。不把知识提升变成每次修复的收尾门槛，也不自动写入全局规范。

相关规范路径相对项目 `AGENTS.md` 或 `CLAUDE.md` 指向的规范仓根；它们不是技能安装目录的相对路径。
